Project: RV-DIS — RISC-V Dual-Issue SIMD Processor
(RV32I scalar + 128-bit SIMD; in-order even/odd dual-issue)

RISC-V 32-bit instructions formate

RV32I Instruction Set Architecture Deisgned:

    a) fixed 32-bit instruction keeps decode and fetch simpler i.e. no mixed instruction lengths

    b) a 3-address style register fields (rd, rs1, rs2) need less instructions than 2-address

    c) Encoding and Decoding is relatively uniform with the same bit positioning for rs1, rs2, rd, expect sign-extended immediates 

    1) sufficient to form a compiler target,
    - reliably generate neccessary machine code

    2) can support modern operating system environments

    3) Reduce hardware required in a minimal implementation
    - verify RTL with Yosys elaboration / synthesis (scripts/run_yosys.ps1)

S1_Fetch:

    Program Counter (PC):

            // external controls 
            input  logic          clk,
            input  logic          rst_n,
            input  logic          enable,

            // internal controls
            input  logic          fetch_stall,
            input  logic          dispatch_stall, 
            input  logic          mode,
            input  logic          spec0_en,

            // input data
            input  logic [31:0]   pc0_in,
            input  logic [31:0]   pc1_in,

            // output data
            output logic          is_spec,
            output logic [31:0]   pc0_out,
            output logic [31:0]   pc1_out

        0. Structure and Specification:

            The PC unit (rtl/s1_fetch/pc.sv) is a registered dual-issue address generator.
            It owns two 32-bit byte addresses — pc0_out and pc1_out — that name the
            instruction pair fetched on the even (I0) and odd (I1) lanes. The module is
            intentionally narrow: it does not decode branches or read the BTB. It only
            (1) aligns incoming bases pc0_in / pc1_in to 4-byte boundaries, (2) adds a
            selected increment when enabled and not stalled, and (3) latches the result on
            the clock edge. Branch targets, fall-through PCs, and recovery addresses are
            supplied by pc_selector; fetch_stall and dispatch_stall come from the fetch
            and dispatch stages. On reset, pc0_out <= RESET_PC and pc1_out <= RESET_PC+4,
            establishing the canonical dual-issue layout where I1 trails I0 by one word.
            The is_spec output is a registered flag that records whether the current PC
            pair was advanced under speculative control (spec0_en).

        1. Dual PC adder with mode selection:

            Both lanes share one combinational next-value path. After alignment,
            pc0_a = {pc0_in[31:2], 2'b00} and pc1_a = {pc1_in[31:2], 2'b00}. When
            enable is high and neither stall is asserted, mode selects the add amount
            applied to both lanes in parallel:

                mode = 0  (sequential dual-issue)  ->  pc0_next = pc0_a + 8,  pc1_next = pc1_a + 8
                mode = 1  (speculative / split)    ->  pc0_next = pc0_a + 4,  pc1_next = pc1_a + 4

            mode=0 is the default sequential step: each lane's base advances by one full
            8-byte bundle (two 32-bit instructions), which matches straight-line dual
            fetch where the next pair is eight bytes ahead of the current pair bases.
            mode=1 is used when pc_selector has routed divergent targets into pc0_in and
            pc1_in (for example I0 on a predicted target and I1 on fall-through); in that
            case both lanes advance by +4 from their respective aligned bases so the PC
            unit tracks two independent 4-byte streams rather than one locked +8 step.
            If enable is low or either fetch_stall or dispatch_stall is high, pc0_next and
            pc1_next hold the current registered outputs — the PC pair does not move.

        2. Branch Speculation and Stalls Behavior:

            Speculation is a cross-module contract between pc_selector and pc.sv, not
            logic inside the PC adder itself. pc_selector drives pc0_in / pc1_in (the
            bases fed into the adder), mode, spec0_en, and fetch_stall; pc.sv consumes
            those signals and exposes is_spec back to the selector.

            spec0_en is latched into is_spec on any enabled, non-stalled update. While
            is_spec is set, a new predict-taken request asserts fetch_stall through
            pc_selector, freezing the PC pair until execute recovery clears the flag.
            That prevents nested speculation on top of an unresolved branch.

            fetch_stall (from pc_selector) blocks PC movement when a predict is attempted
            while already in a speculative fetch. dispatch_stall (from the dispatch stage)
            blocks PC movement independently — for example while holding fetch during a
            BTB write or a dispatch back-pressure event — without clearing is_spec.

            On branch recovery (i0_brch_recover or i1_brch_recover), pc_selector reloads
            pc0_in / pc1_in from execute-stage PCs, clears speculation via spec0_en, and
            sets mode=0 so the next enabled cycle resumes +8/+8 sequential advance from
            the recovered pair. Wrong predictions fall back to the execute address;
            correct predictions continue from the recovered stream with flush handled
            downstream in decode/dispatch, not inside pc.sv.

    Program Selector (PC_Selector):

            // internal controls
            input  logic          is_spec,
            input  logic          i0_pred_taken,
            input  logic          i1_pred_taken,
            input  logic          i0_brch_recover,
            input  logic          i1_brch_recover,

            // input data
            input  logic [31:0]   pc0_in,
            input  logic [31:0]   pc1_in,
            input  logic [31:0]   i0_pc_target,
            input  logic [31:0]   i1_pc_target,
            input  logic [31:0]   i0_pc_execute,
            input  logic [31:0]   i1_pc_execute,

            // output data
            output logic          stall,
            output logic          mode,
            output logic          spec0_en,
            output logic [31:0]   pc0_out,
            output logic [31:0]   pc1_out

        0. Structure and Specification:

            pc_selector (rtl/s1_fetch/core_mod/pc_selector.sv) is a purely combinational
            routing block between the registered PC pair, the branch target buffer, and
            execute-stage recovery. It does not increment addresses — that is pc.sv's
            job. Each cycle it observes the live fetch PCs (pc0_in, pc1_in), BTB targets
            (i0_pc_target, i1_pc_target), and resolved execute PCs (i0_pc_execute,
            i1_pc_execute), then drives pc0_out / pc1_out as the aligned bases that pc.sv
            will add to on the next enabled update. It also exports three control signals
            consumed by pc.sv: stall (wired as fetch_stall in fetch_core_struct),
            mode, and spec0_en. The registered is_spec flag from pc.sv is fed back so
            the selector can block nested predicts while a prior speculation is still
            in flight.

        1. Dual PC Selection Priority without speculation:

            With no predict and no recovery active, the default path simply aligns the
            current fetch pair: pc0_out = align(pc0_in), pc1_out = align(pc1_in). All
            targets and execute addresses are ignored. This is the straight-line case
            where pc.sv will apply mode=0 and advance both lanes by +8 from these bases.

            When a predict is taken, selection follows fixed priority in the combinational
            mux (recovery overrides predict; see sections 3–4):

                i0_pred && i1_pred  ->  pc0_out = align(i0_pc_target),
                                        pc1_out = align(i0_pc_target) + 4
                i0_pred only        ->  pc0_out = align(i0_pc_target),
                                        pc1_out = align(pc1_in)
                i1_pred only        ->  pc0_out = align(i1_pc_target),
                                        pc1_out = align(pc0_in)

            The i0+i1 both-taken case forms a contiguous target pair from I0's BTB entry.
            The single-lane cases keep the other slot on its sequential in-pair PC so
            one lane follows the predicted target while the other retains fall-through.

        2. Mode and Control signals:

            Three outputs encode how pc.sv should treat the next update:

                spec0_en  — 1 when entering or already in speculative fetch; latched by
                            pc.sv as is_spec on the next enabled, non-stalled cycle.
                mode      — 1 when exactly one of i0_pred_taken / i1_pred_taken is set
                            (XOR), selecting +4/+4 advance in pc.sv; 0 for sequential
                            +8/+8 or recovery.
                stall     — 1 when a new predict is requested while is_spec is already
                            set (fetch_stall to pc.sv).

            All three are suppressed when recover_any = i0_brch_recover | i1_brch_recover
            is true, so recovery always returns control to non-speculative +8/+8 stepping.

        3. Branch Speculation and Stalls Behavior:

            A predict-taken on either lane asserts spec0_en (unless recovery is active),
            telling pc.sv to enter or remain in speculative fetch. If only one lane predicts
            taken, mode=1 and pc.sv advances each aligned base by +4, tracking split streams.
            If both lanes predict taken, mode=0 because (i0_pred ^ i1_pred) is false; pc.sv
            still advances +8/+8 from the rerouted target pair bases.

            While is_spec is registered in pc.sv, any new i0_pred_taken or i1_pred_taken
            without a concurrent recovery asserts stall=1. That freezes the PC pair at
            pc.sv until execute resolves the outstanding branch and recovery clears
            is_spec. This blocks stacking a second speculative redirect on an unresolved
            first branch. Dispatch-stage stalls are not generated here; they enter pc.sv
            separately as dispatch_stall.

        4. Branch Recovery and Un-Stalls Behavior:

            Recovery has highest priority in the PC mux. If i0_brch_recover is set, both
            outputs are rebuilt from I0's execute PC: pc0_out = align(i0_pc_execute),
            pc1_out = align(i0_pc_execute) + 4. Otherwise, if i1_brch_recover is set, the
            same pair layout uses i1_pc_execute. Recovery clears spec0_en, mode, and stall
            in the same cycle, so pc.sv resumes non-speculative +8/+8 from the recovered
            bases on the next enabled update.

            Un-stall occurs because recovery deasserts stall and spec0_en while is_spec
            clears in pc.sv after the recovered update. Until then, predicts during is_spec
            continue to assert stall; after recovery, new predicts are allowed again.
            Wrong predictions redirect to the execute-stage pair; correct predictions
            realign the fetch window, with pipeline flush handled outside pc_selector.

    Insturction Cache (Instruction_Cache):

            //external controls
            input  wire     clk,
            input  wire     rst_n,

            //input data
            input  word_t   pc0,
            input  word_t   pc1,

            //output data
            output instr_t  instr0,
            output instr_t  instr1

        0. Structure and Specification:

            instruction_cache (rtl/s1_fetch/core_mod/instruction_cache.sv) is a
            dual-port instruction store sized for the 32 KiB RV32I fetch space.
            Lookups are combinational; the bank is cleared on reset (clk/rst_n) and
            preloaded by simulation (or external load) until sequential miss handling
            is added. Each stored entry is 33 bits: a valid bit plus one 32-bit
            little-endian instruction word (ILEN=32). The array is 4-way
            set-associative over PC[14:2]: INDEX_W = 13 index bits, 8192 logical
            slots, 2048 sets × 4 ways. Set and way decode use cache_pkg::pc_set and
            cache_pkg::pc_way from the fetch PCs. The module exposes pc0/pc1 in and
            instr0/instr1 out; it does not yet arbitrate misses, refill, or coherence.

        1. Combinational Dual Instruction Address Read:

            Both ports read independently in the same cycle. Port I0 indexes
            bank[i0_lookup_set][i0_lookup_way] from pc0; port I1 indexes
            bank[i1_lookup_set][i1_lookup_way] from pc1. Each lookup is
            combinational through cache_way_read: if the selected entry's valid bit
            is set, instrN is the stored word; if valid=0 (cold miss), the default
            data 32'h0 is returned. There is no fall-through PC-based default — an
            empty slot is indistinguishable from a real all-zero instruction unless
            valid is set.

            Because indexing is direct-mapped by PC set/way (not tag compare), each
            PC maps to exactly one bank location. Dual fetch therefore works for any
            pc0/pc1 pair, including sequential pairs (pc, pc+4) and identical PCs on
            both ports. The two reads do not block each other; they are two parallel
            cache_way_read calls on separate bank cells. In fetch_core_struct, pc0 and
            pc1 from pc.sv drive instr0/instr1 into the decode stage on the same cycle
            as the address presentation.

        2. Sequential Cache Instruction Miss (Working Progress):

            Not implemented in current RTL. Planned: sequential miss detect, external
            memory refill, valid install, and fetch stall until both requested lines
            are present.

    Branch Target Buffer (Target_Buffer):

            //external controls
            input  wire        clk,
            input  wire        rst_n,

            //internal controls
            input  wire        i0_valid_wb,
            input  wire        i1_valid_wb,

            //input data
            input  word_t      i0_pc,
            input  word_t      i1_pc,
            input  word_t      i0_pc_wb,
            input  word_t      i1_pc_wb,
            input  word_t      i0_pc_target_wb,
            input  word_t      i1_pc_target_wb,

            //output data
            output wire [31:0] i0_pc_target,
            output wire [31:0] i1_pc_target

        0. Structure and Specification:

            target_buffer (rtl/s1_fetch/core_mod/target_buffer.sv) is the fetch-stage
            branch target buffer (BTB). The bank is clocked storage; lookups are
            combinational dual read with same-cycle writeback forwarding. The bank
            mirrors the 32 KiB instruction address space: INDEX_W = 13 over PC[14:2],
            8192 logical slots arranged as 512 sets × 16 ways (higher associativity
            than the I$). Each entry is 33 bits — valid plus a 32-bit aligned branch
            target. Set and way decode use cache_pkg::pc_set and cache_pkg::pc_way
            from the lookup PCs and from i0_pc_wb / i1_pc_wb on train. The module
            does not decide predict-taken; it only supplies i0_pc_target and
            i1_pc_target to pc_selector. Execute-stage i0_valid_wb / i1_valid_wb
            qualify training writes that install or overwrite the target for the
            branch PC at WB.

        1. Combinational Dual Read with Forwarding:

            Each cycle both ports look up independently from i0_pc and i1_pc. For each
            port, way_with_forward selects bank[set][way] unless a valid WB in the same
            cycle targets that same set/way — then the incoming WB entry wins (I0 WB
            checked before I1 WB). cache_way_read returns the stored target when valid=1;
            on miss (valid=0) it returns fallthrough = pc+4 for that lane. Lookups are
            combinational; outputs update in the same cycle as the presented fetch PCs.

        2. Sequential Falling-edge Dual Writeback:

            Training commits on the falling clock edge when i0_valid_wb or i1_valid_wb is
            set. The write index is derived from i0_pc_wb / i1_pc_wb; the stored data is
            imm_align4(i0_pc_target_wb / i1_pc_target_wb) with valid forced to 1 via
            cache_set_write. Dual WB in one cycle can update two distinct slots; if both
            trains map to the same set/way, both nonblocking writes fire and the I1
            update is the final value in that slot. Because forwarding is evaluated
            before the edge, a train visible on cycle N is readable on port outputs in
            cycle N even though the bank register updates after the edge — the read path
            always sees the freshest target for pc_selector in fetch_core_struct.

S2_Decode:

    Intermediate Register (IF_ID):

            // external controls
            input  logic        clk,
            input  logic        rst_n,
            input  logic        enable,

            // internal controls
            input  logic        flush,
            input  logic        stall,

            // input data
            input  instr_t      i0_instr_if,
            input  instr_t      i1_instr_if,
            input  word_t       i0_pc_if,
            input  word_t       i1_pc_if,
            input  word_t       i0_pc_target_if,
            input  word_t       i1_pc_target_if,

            // output data
            output instr_t      i0_instr_id,
            output instr_t      i1_instr_id,
            output word_t       i0_pc_id,
            output word_t       i1_pc_id,
            output word_t       i0_pc_target_id,
            output word_t       i1_pc_target_id

        0. Structure and Specification:

            if_id (rtl/s2_decode/if_id.sv) is the pipeline register between fetch (IF) and
            decode (ID). An instruction is in IF or ID, not both; this module is the cycle
            boundary where the dual-issue pair is captured for decode. It is a single
            registered stage with no combinational decode — it only stores and forwards
            six fields per lane bundle: instruction word, fetch PC, and fetch-stage
            predicted branch target. pc_target_* is carried alongside the insn so ID and
            later stages can compare against resolved execute targets for mispredict
            recovery. clk/rst_n/enable are the global pipeline controls; flush and stall
            are stage-local back-pressure and redirect inputs from upstream fetch or
            downstream decode/dispatch.

        1. Dual Issue Input and Output:

            Both lanes update together on the same conditions. IF presents i0_instr_if /
            i1_instr_if from the instruction cache, i0_pc_if / i1_pc_if from the PC unit,
            and i0_pc_target_if / i1_pc_target_if from the branch target buffer. When the
            register advances, all six outputs latch in parallel into i0_instr_id,
            i1_instr_id, i0_pc_id, i1_pc_id, i0_pc_target_id, and i1_pc_target_id. There
            is no per-lane enable — I0 and I1 are always a pair. A sequential dual-fetch
            cycle presents (pc, pc+4) with matching targets; after a predict or recovery
            reroute, the pair may name divergent streams, but the register still captures
            whatever IF validly drove that cycle.

        2. Stalls and Flush control:

            Update priority in the always_ff block is: async reset, then flush, then
            enable&&!stall advance, else hold.

                rst_n low     ->  all ID outputs driven to zero
                flush high    ->  same clear on the next clock edge (bubble both lanes)
                enable&&!stall ->  capture current IF inputs into ID
                otherwise     ->  hold previous ID state

            flush is used on branch mispredict or pipeline redirect: the stage is emptied
            so decode does not consume stale instructions after fetch realigns. stall
            freezes the register without clearing — IF may continue presenting, but ID
            keeps the prior pair until back-pressure releases. If enable is low, no
            advance occurs even when stall is low; the stage holds. flush and stall are
            not mutually exclusive in the port list, but flush takes precedence when
            asserted on a clock edge.

    Decoder:

            // input data
            input  instr_t      instr,

            // output data
            output logic        lane_sel,
            output logic        brch_en,
            output opcode_t     opcode,
            output funct3_t     funct3,
            output funct7_t     funct7,
            output gpr_addr_t   rd,
            output gpr_addr_t   rs1,
            output gpr_addr_t   rs2,
            output word_t       imm,

            // output controls
            output logic        valid,     // 1 when insn is legal for RV-DIS scalar decode
            output logic        rs1_use,
            output logic        rs2_use,
            output logic        reg_write

        0. Structure and Specification:

            decoder (rtl/s2_decode/core_mod/decoder.sv) is a purely combinational
            RV32I scalar decode block for one instruction slot. It accepts a single
            32-bit instr word and drives decoded opcode/funct3/funct7, GPR indices
            (rd, rs1, rs2), a sign-extended immediate, and control qualifiers for
            downstream register read and dispatch. Field extraction and legality tables
            live in decode_pkg (rtl/s2_decode/funct_pkg/decode.sv); the module itself
            is only wiring: raw opcode/funct3 are sampled first, then GPR-specific
            decoders zero unused register fields per opcode rules. valid asserts when
            the insn is in the implemented RV-DIS scalar subset; brch_en is valid &&
            a branch/jump opcode. The decoder does not read the register file or issue
            to execution — that integration is in decode_core_struct and dispatch.

        1. Two Decoders for Instruction Parallelism:

            Dual issue is implemented by replicating the same decoder module twice in
            s2_decode_struct: u_dec_i0 decodes i0_instr, u_dec_i1 decodes i1_instr.
            Both instances run in parallel every cycle with identical logic and no
            cross-coupling inside decode. Each copy exports its own lane_sel, opcode
            bundle, imm, valid, brch_en, rs1_use/rs2_use, and reg_write. GPR read
            addresses from each decoder feed register_file on internal nets and are
            also re-exported as i0_rs1_addr / i0_rs2_addr and i1_rs1_addr /
            i1_rs2_addr for dispatch. Throughput is two independent decode results
            per cycle; pairing legality and which lane may fire are decided later in
            dispatch, not inside decoder.sv.

        2. Instruction Lane Differentiation:

            lane_sel tags which execution lane owns the opcode class: lane_sel=0 for
            even-lane ops (OP, OP-IMM — ALU work on I0), lane_sel=1 for odd-lane ops
            (LOAD, STORE, BRANCH, JAL, JALR, LUI, AUIPC — memory, branch, and upper-
            immediate work on I1). Unknown opcodes default lane_sel=0 but valid=0 so
            dispatch can squash illegal slots. brch_en marks branch/jump insns when
            valid. rs1_use and rs2_use gate register-file read enables; reg_write
            suppresses writes to x0. Together, lane_sel and valid let the pipeline
            route each insn of a fetched pair to the correct even/odd datapath while
            rejecting encodings outside the supported LW/SW and BEQ/BNE/BLT/BGE subset.

    Register File (Register_File):

            // external controls
            input  logic        clk,
            input  logic        rst_n,

            // internal controls
            input  logic        i0_rs1_use,
            input  logic        i0_rs2_use,
            input  logic        i1_rs1_use,
            input  logic        i1_rs2_use,
            input  logic        i0_valid_wb,
            input  logic        i1_valid_wb,

            // input data
            input  gpr_addr_t   i0_rs1_addr,
            input  gpr_addr_t   i0_rs2_addr,
            input  gpr_addr_t   i1_rs1_addr,
            input  gpr_addr_t   i1_rs2_addr,
            input  gpr_addr_t   i0_rd,
            input  gpr_addr_t   i1_rd,
            input  word_t       i0_data_wb,
            input  word_t       i1_data_wb,
            input  word_t       i0_pc_wb,
            input  word_t       i1_pc_wb,

            // output data
            output word_t       i0_rs1_data,
            output word_t       i0_rs2_data,
            output word_t       i1_rs1_data,
            output word_t       i1_rs2_data

        0. Structure and Specification:

            register_file (rtl/s2_decode/core_mod/register_file.sv) is the dual-issue
            scalar GPR file for RV32I: four combinational read ports (I0 rs1/rs2, I1
            rs1/rs2) and two writeback ports (I0/I1). Physical storage is x1–x31;
            x0 is not stored — reads of x0 always return zero and writes to x0 are
            suppressed. Decode supplies rs1_use/rs2_use and addresses; writeback
            supplies i0_valid_wb/i1_valid_wb, rd, data, and insn PC (i0_pc_wb /
            i1_pc_wb) for same-cycle WAW merge. There is no enable — commits occur
            on the falling clock edge whenever a valid WB targets a nonzero rd. clk/rst_n
            clear the array on reset.

        1. Combinational Dual Read with Forwarding:

            Each read port is independent. When rs_use is low, the port drives zero
            (unused operand). When rs_use is high, rf_read_port returns the stored
            value unless a valid WB in the same cycle writes that rd — then the WB
            data wins (forwarding). I0 and I1 WB can both forward in one cycle; if both
            write the same rd, the higher i0_pc_wb / i1_pc_wb selects the younger insn
            (i1 wins on tie or greater PC). Bypass is visible to ID before the bank
            updates. Cross-lane bypass is supported: an ID read on either lane can see
            the other lane's pending WB when addresses match.

        2. Sequential Falling-edge Dual Writeback:

            Training commits on negedge clk when i0_valid_wb or i1_valid_wb is set and
            rd != x0. Dual WB can update two distinct registers in one cycle. If both
            lanes write the same rd, only the younger insn (by i0_pc_wb vs i1_pc_wb)
            updates regs[] — the older commit is suppressed. Forwarding on the read path
            still exposes the winning WB value in that cycle before the falling edge.
            After the edge, subsequent reads see the committed value from regs[].

    Branch State Buffer (State_Buffer):

            // external controls
            input  logic        clk,
            input  logic        rst_n,

            // internal controls 
            input  logic        i0_brch_en,
            input  logic        i1_brch_en,
            input  logic        i0_valid_wb,
            input  logic        i1_valid_wb,

            // input data
            input  word_t       i0_pc,
            input  word_t       i1_pc,
            input  word_t       i0_pc_wb,
            input  word_t       i1_pc_wb,
            input  br_state_t   i0_target_state_wb,
            input  br_state_t   i1_target_state_wb,

            // output data
            output br_state_t   i0_target_state,
            output br_state_t   i1_target_state

        0. Structure and Specification:

            state_buffer (rtl/s2_decode/core_mod/brch_predict_units/state_buffer.sv)
            is the branch-direction predictor table (BHT/BTB companion). It stores a
            2-bit saturating counter state (br_state_t) per branch PC, indexed like
            the BTB: INDEX_W = 13 over PC[14:2], 8192 slots, 512 sets × 16 ways.
            Each bank entry is 33 bits — valid plus 2-bit state. Set/way decode uses
            cache_pkg::pc_set and cache_pkg::pc_way. Miss (valid=0) defaults to
            DEFAULT_STATE (2'b01, weakly not taken). i0_brch_en / i1_brch_en gate
            whether a lane performs a real lookup; non-branch insns drive
            DEFAULT_STATE on the outputs without treating the bank as taken. WB
            trains from execute via i0_valid_wb / i1_valid_wb with branch PC and
            updated i0_target_state_wb / i1_target_state_wb.

        1. Combinational Dual Read with Forwarding:

            Both ports look up independently from i0_pc and i1_pc when brch_en is
            set for that lane. way_with_bypass reads bank[set][way] unless a valid
            WB in the same cycle targets that slot — then the incoming WB entry wins
            (I0 WB checked before I1 WB). cache_way_read returns the stored 2-bit
            state when valid=1; on miss it returns DEFAULT_STATE. The final output
            mux applies brch_en: branch lanes expose raw_state; non-branch lanes
            force DEFAULT_STATE. Lookups are combinational; predictors see the
            result in the same cycle as the presented fetch PCs.

        2. Sequential Rising-edge Dual Writeback:

            Training commits on the rising clock edge when i0_valid_wb or
            i1_valid_wb is set. The write index is i0_pc_wb / i1_pc_wb; stored
            data is the 2-bit i0_target_state_wb / i1_target_state_wb with valid
            forced to 1. Dual WB in one cycle can update two distinct slots; if both
            trains map to the same set/way, both nonblocking writes fire and the I1
            update is the final value. Because forwarding is evaluated before the
            edge, a train visible on cycle N is readable on port outputs in cycle N
            even though the bank register updates after the edge.
