Project: RV-DIS: RISC-V Dual-Issue Out-of-Order Processor
(RV32I scalar; dual-issue with rename / ROB / OoO issue)

RISC-V 32-bit Instruction Format

RV32I Instruction Set Architecture Designed:

    The instruction set is built around fixed 32-bit instructions for
    simpler fetch and decode with no mixed instruction lengths, and a
    uniform 3-address destination / source1 / source2 register layout that
    needs fewer instructions than a 2-address style. Field placement is
    uniform — both sources and the destination sit at the same bit
    positions across formats, with the immediate sign-extended — which is
    sufficient to target a compiler or OS toolchain for codegen and modern
    OS environments, while keeping a minimal hardware footprint for a
    compact RV32I dual-issue core suitable for FPGA or ASIC
    implementation.

S1_Fetch:

    Overview:
        Path: `rtl/s1_fetch/fetch_core_struct.sv`

        Instantiates the program counter unit, instruction cache, branch
        target buffer, and program selector. All slot-indexed ports are
        two-element arrays: index 0 is lane I0, index 1 is lane I1. The
        registered fetch addresses feed both the instruction cache and the
        target buffer lookups; the cache's per-lane present flags and the
        buffer's predicted targets pass straight through to the struct
        outputs for the IF/ID boundary and decode. The program selector
        computes the next-PC bases and the next-cycle speculation pair that
        feed the program counter unit; that unit feeds its registered
        speculation flags back into the selector. Sequential versus split
        stride (+4/+4 vs +8/+8) is computed inside the program counter from
        whether exactly one of the next-spec bits is set. Nested-speculation
        freeze enters as per-lane stalls from decode's target predictor
        (not generated inside the selector). Predict-taken and execute
        recovery are driven from outside and steer the selector directly.

        The selector's redirect target is not the target buffer's own lookup
        output — it is an external decode-predicted target presented at the
        struct boundary. Decode's currently computed predicted target is
        wired both into the buffer's training ports (alongside the branch
        PCs and train-valid flags) and into the selector's redirect input,
        so the same decode value teaches the BTB and steers fetch in the
        same cycle. The buffer's own combinational lookup result — exported
        as the struct's predicted-target outputs, indexed by the registered
        fetch PCs — is a separate path: the predicted target for the
        instruction currently being fetched, forwarded to IF/ID / decode,
        and is not looped back into the selector.

        Per-lane speculation: Speculative fetch is lane-owned. If I0 takes a
        branch, I0 follows the taken path and holds that lane's speculation
        flag; if I1 takes a branch, I1 follows the taken path and holds its
        own flag. There is no forced remapping that always puts the taken
        stream on I0 and fall-through on I1. That keeps IF/ID/decode
        speculation enables aligned with which slot actually speculated
        (so a branch fetched in I1 does not falsely mark I0 as speculative).

    Program Counter (PC):
            Path: `rtl/s1_fetch/core_mod/pc.sv`

            // external controls
            input  logic          clk,
            input  logic          rst_n,
            input  logic          enable,

            // internal controls
            input  logic          dispatch_stall,
            input  logic          spec_stall [2],
            input  logic          spec_in    [2],

            // input data
            input  word_t         pc_in      [2],

            // output data
            output word_t         pc_out     [2],

            // output controls — registered speculation (fed back to pc_selector)
            output logic          spec_out   [2]

        0. Structure and Specification:

            The program counter unit is a registered dual-issue address
            generator. It owns two 32-bit byte addresses for the I0 and I1
            fetch lanes, plus two registered path selectors: zero denotes
            path0 and one denotes path1. The flags are independent — each
            tracks only its own lane. The module does not decode branches or
            read the BTB. It only (1) aligns both incoming bases to 4-byte
            boundaries, (2) computes local mode from the next-spec bits and
            adds the selected increment when enabled and not stalled, and
            (3) latches PCs and speculation flags on the clock edge. Bases
            and next-spec bits come from the program selector. Stall is the
            OR of dispatch back-pressure and either nest-speculation stall.
            The combinational next addresses default to holding the currently
            registered pair; they are only overwritten with the aligned and
            incremented value when enabled and not stalled, and the register
            update gates on that same condition, so a stall is an exact hold.
            On reset, lane I0 starts at the reset PC, lane I1 at reset PC
            plus four, and both speculation flags clear.

        1. Dual PC adder with mode selection:

            Local mode is the XOR of the two next-spec bits (exactly one
            next-spec lane). When enable is high and neither stall is
            asserted, mode selects the increment added to each lane's
            aligned base.

            Mode 0, sequential dual-issue, is the straight-line case: both
            lanes advance by eight bytes from their aligned bases. Mode 1,
            speculative / split, lets each lane advance its own stream by
            four bytes instead.

            If enable is low or any stall is high, PCs and speculation flags
            hold; the pair does not move.

        2. Branch Speculation and Stalls Behavior:

            Speculation is a cross-module contract. The program selector
            drives the next bases and next-spec bits; the program counter
            latches them and feeds the registered flags back to the
            selector. Nested-speculation stall is produced in decode's
            target predictor and enters here as the per-lane stall inputs
            (not from the selector). Because each flag is lane-local, a
            decode nest-stall for a lane only trips when that same lane's
            registered speculation flag is already set.

            The next-spec bits travel from the selector into the program
            counter as the next per-lane speculative state, latched on every
            enabled update; those same bits also form mode (XOR gives +4/+4,
            equality gives +8/+8). The registered flags travel the other
            direction, back to the selector, for the next-spec computation.
            Nest stalls arrive from decode and freeze the PC when a branch
            or jump arrives while that lane is already speculative. Dispatch
            stall freezes the PC independently, holding both PC and
            speculation flags.

            On recovery, the selector clears both next-spec bits (mode 0)
            and reloads bases past the resolved branch (execute address
            plus four / plus eight). Pipeline flush lives in decode /
            dispatch, not in the program counter unit.

    Program Selector (PC_Selector):
            Path: `rtl/s1_fetch/core_mod/pc_selector.sv`

            // internal controls
            input  logic          spec_in      [2],
            input  logic          pred_taken   [2],
            input  logic          brch_recover [2],

            // input data
            input  word_t         pc_in        [2],
            input  word_t         pc_target    [2],
            input  word_t         pc_execute   [2],

            // output controls
            output logic          spec_out     [2],

            // PC bases → pc (pc_in)
            output word_t         pc_out       [2]

        0. Structure and Specification:

            The program selector is a purely combinational routing block
            among the registered PC pair, a per-lane redirect target, and
            execute recovery. It does not apply the sequential / split
            stride; that is the program counter's job (local mode from
            next-spec XOR). Each cycle it drives aligned bases that the
            program counter will add to, plus next per-lane speculation
            flags. It does not generate a fetch stall: nested speculation
            is blocked in decode by the target predictor, which freezes the
            program counter via the nest-stall inputs.

            The module's redirect-target port is generic; in the fetch
            struct it is wired not to the target buffer's own BTB lookup
            output, but to the external decode-predicted target (see
            Overview). The same value simultaneously trains the BTB and
            steers this redirect, so decode's currently computed predicted
            target both teaches the BTB and redirects fetch in the same
            cycle.

            Taken versus fall-through is per predicting lane (not a fixed
            I0-taken / I1-fall-through convention). A predict on I0 steers
            that lane's base to the target; a predict on I1 steers I1's base
            to the target.

        1. Dual PC Selection Priority without speculation:

            Default (no predict, no recovery): both bases are the aligned
            registered PCs; the program counter then applies +8/+8 (mode 0).

            Predict mux (recovery overrides; see §4): when both lanes are
            predicted taken, I0 takes the aligned I0 target and I1 takes
            that same target plus four. When only I0 is predicted taken, I0
            takes the aligned I0 target while I1 stays on its aligned
            registered PC. When only I1 is predicted taken, I0 stays on its
            aligned registered PC while I1 takes the aligned I1 target.

            I1-only predict: only I1 updates to the branch target (the
            speculative path stays on I1); next-spec becomes asymmetric so
            the program counter enters mode 1 (+4/+4). I0 is left as its
            aligned registered base — by the time predict feeds back, that
            registered I0 value is already the next-cycle base from the
            prior +8 advance, so I0 does not need an extra +4 nudge here.

        2. Control signals:

            Each next-spec flag asserts when that lane is predicted taken or
            already speculative, and neither recovery is active; both are
            latched and feed the program counter's mode computation via XOR.
            Recovery on either lane clears both next-spec bits. Speculation
            is sticky per lane: only the predicting lane's flag ORs in; the
            other lane is not forced speculative. Recovery clears both
            next-spec bits so the program counter mode goes to 0.

        3. Branch Speculation Behavior:

            With neither lane predicted taken, next-spec stays clear, PC
            mode stays 0, and both lanes advance by +8 — the straight-line
            or post-recovery case. When only I0 is predicted taken,
            next-spec becomes I0 speculative / I1 not, PC mode goes to 1,
            and both lanes advance by +4, with I0 taken and I1 falling
            through. When only I1 is predicted taken, next-spec becomes I0
            not / I1 speculative, PC mode again goes to 1 with +4/+4
            increments, I1 taken and I0's base left unchanged. When both
            lanes are predicted taken, next-spec becomes both set, PC mode
            returns to 0, and both lanes advance by +8 as the I0 target
            pair.

            Nested branch or jump while that lane is already speculative is
            stalled by decode's target predictor, which freezes the program
            counter via the nest-stall inputs; this module does not assert a
            stall of its own.

        4. Branch Recovery Behavior:

            Recovery has highest priority; resume past the resolved branch.
            I0 recovery takes first priority: I0 becomes the aligned execute
            address plus four, and I1 becomes that same address plus eight.
            Failing that, I1 recovery takes second priority with the same
            +4 / +8 offsets from the I1 execute address.

            Recovery clears next-spec (mode 0); the program counter resumes
            +8/+8 from the post-branch pair on the next enabled update.
            Flush remains outside the program selector.

    Instruction Cache (Instruction_Cache):
            Path: `rtl/s1_fetch/core_mod/instruction_cache.sv`

            //external controls
            input  wire     clk,
            input  wire     rst_n,

            //input data (dual-issue slot pair)
            input  word_t   pc    [2],

            //output data
            output instr_t  instr [2],
            output logic    valid [2]

        0. Structure and Specification:

            The instruction cache is the fetch-stage dual-port instruction
            store for the 32 KiB RV32I I$ space. The program counter is
            byte-addressed, while each bank cell holds one aligned 32-bit
            little-endian instruction word plus a valid bit (a 33-bit packed
            entry). A 13-bit index over PC bits [14:2] selects among 8192
            logical slots. Lookups are combinational; clock and reset clear
            the bank on reset. Until sequential miss/refill exists, an
            external loader preloads valid entries. The module exposes a
            dual fetch-PC input and dual instruction / present outputs and
            does not yet arbitrate misses, refill, or coherence.

        1. 2-way Set-Associative Bank (4-byte instruction word per entry):

            The bank is organized as 2 ways and 4096 sets: 4096 sets of two
            ways, for 8192 × 4 B = 32 KiB of instruction payload. Shared
            set/way helpers map each fetch PC to one cell with way from
            PC[2] and set from PC[14:3], so each entry stores a valid bit
            plus one full RV32I word, not a single byte. Two-way
            associativity is chosen as the minimum that matches dual-issue
            fetch: a straight-line pair (PC, PC+4) are consecutive word
            addresses that differ only in PC[2], so they land in the same
            set on ways 0 and 1 and can be read in parallel without a
            same-way bank conflict. An 8-byte aligned dual-issue bundle
            therefore maps onto both ways of one set, which is exactly the
            dual PC window produced by the program counter. Each port still
            indexes independently, so any dual PC pair is legal; the
            two-way layout makes the common sequential dual-fetch case a
            natural dual hit inside one set.

        2. Combinational Dual Instruction Address Read:

            Both ports read independently in the same cycle. Each port
            indexes its bank cell from its fetch PC. If the selected
            entry's valid bit is set, that lane's instruction is the stored
            word; on a cold miss the default data of all zeros is returned.
            The present flag exports that same entry valid bit so a cold
            miss is distinct from a stored all-zero word.

            Because indexing is direct-mapped by PC set/way (not tag
            compare), each PC maps to exactly one bank location. Dual fetch
            therefore works for any dual PC pair, including sequential pairs
            and identical PCs on both ports. The two reads do not block each
            other; they are two parallel way reads on separate bank cells.
            In the fetch struct, the registered PC pair drives instructions
            into the decode stage on the same cycle as the address
            presentation.

        3. Sequential Cache Instruction Miss (Working Progress):

            Not implemented in current RTL. Planned: sequential miss detect,
            external memory refill, valid install, and fetch stall until both
            requested lines are present.

    Branch Target Buffer (Target_Buffer):
            Path: `rtl/s1_fetch/core_mod/target_buffer.sv`

            //external controls
            input  wire        clk,
            input  wire        rst_n,

            //internal controls
            input  logic       valid_wb     [2],

            //input data (dual-issue slot pair)
            input  word_t      pc           [2],
            input  word_t      pc_wb        [2],
            input  word_t      pc_target_wb [2],

            //output data
            output logic       valid        [2],
            output word_t      pc_target    [2]

        0. Structure and Specification:

            The target buffer is the fetch-stage branch target buffer (BTB).
            Lookups are combinational dual read with same-cycle writeback
            forwarding; the bank trains on the falling clock edge. The
            module does not decide predict-taken: it only reports per-port
            hit flags and predicted targets for downstream fetch/select
            logic. Despite the writeback naming on the train ports, those
            ports are driven from outside the fetch struct by decode's
            predicted-branch path (the same decode-predicted target that also
            steers the program selector — see Overview), not by execute
            writeback; they qualify training writes that install or overwrite
            the target for that branch PC. Clock and reset clear the bank on
            reset.

        1. 16-way Set-Associative Bank (4-byte aligned target per entry):

            The bank is organized as 16 ways and 512 sets: 512 sets of
            sixteen ways, for 8192 logical slots over the same 13-bit /
            PC[14:2] space as the 32 KiB I$. Each cell is a 33-bit packed
            entry: valid plus a 32-bit aligned branch target (not an
            instruction word). Shared set/way helpers map each lookup or
            train PC to one cell. Higher associativity than the I$ (16-way
            vs 2-way) gives more distinct branch PCs room in the same
            address window without changing the PC index width. Each port
            still indexes independently, so any dual PC pair is legal.

        2. Combinational Dual Read with Forwarding:

            Each cycle both ports look up independently from the dual fetch
            PCs. For each port, the forwarded entry selects the bank cell
            unless a valid train in the same cycle targets that same set/
            way; then the incoming train entry wins (I0 train checked before
            I1). The hit flag is the forwarded entry's valid bit and is
            independent per port: a miss or stored invalid on one port clears
            only that port's hit. The way read returns the stored target on
            a hit; on miss it returns all zeros for that lane while the hit
            flag stays clear. Lookups are combinational; outputs update in
            the same cycle as the presented fetch PCs.

        3. Sequential Falling-edge Dual Writeback:

            Training commits on the falling clock edge when either train-
            valid is set. The write index is derived from the train branch
            PCs; the stored data is the aligned train target with valid
            forced set. Dual train in one cycle can update two distinct
            slots; if both trains map to the same set/way, both nonblocking
            writes fire and the lane-1 update is the final value in that
            slot. Because forwarding is evaluated before the edge, a train
            visible on cycle N is readable on port outputs in cycle N even
            though the bank register updates after the edge; the read path
            always sees the freshest hit/target for the program selector in
            the fetch struct.

Intermediate Register (IF_ID):

            Path: `rtl/s2_decode/if_id.sv`

            // external controls
            input  logic        clk,
            input  logic        rst_n,
            input  logic        enable,

            // internal controls
            input  logic        flush,
            input  logic        stall,
            input  logic        fetch_valid_if  [2],
            input  logic        target_valid_if [2],
            input  logic        spec_en_if      [2],

            // input data
            input  instr_t      instr_if        [2],
            input  word_t       pc_if           [2],
            input  word_t       pc_target_if    [2],

            // output data
            output  instr_t     instr_id        [2],
            output  word_t      pc_id           [2],
            output  word_t      pc_target_id    [2],

            // output controls
            output  logic       fetch_valid_id  [2],
            output  logic       target_valid_id [2],
            output  logic       spec_en_id      [2]

        0. Structure and Specification:

            The IF/ID register is the pipeline register between fetch and
            decode. An instruction is in fetch or decode, not both; this
            module is the cycle boundary where the dual-issue pair is
            captured for decode. It is a single registered stage with no
            combinational decode; it stores and forwards per lane: instruction
            word, fetch PC, predicted branch target, I$ hit flag, BTB hit
            flag, and speculation enable. The predicted target is carried
            alongside the instruction so decode and later stages can compare
            against resolved execute targets for mispredict recovery. Global
            clock, reset, and enable are the pipeline controls; flush and
            stall are stage-local back-pressure and redirect inputs from
            upstream fetch or downstream decode/dispatch.

            Unlike a design that forces a bubble on a per-lane miss, this
            register does no such gating itself: the I$ and BTB hit flags
            are captured as plain data alongside the instruction on every
            enabled update, whether or not they are set. Downstream
            decode/dispatch is responsible for interpreting a captured miss.
            Only global reset or flush forces the NOP bubble (see §2).

        1. Dual Issue Input and Output (atomic per-cycle capture):

            Both lanes update together, unconditionally, whenever enable is
            high and stall is low — a single dual-lane loop in one sequential
            block, with no per-lane hit gate inside the register itself. Per
            lane, the instruction cache word latches into the decode-side
            instruction; the program counter address latches into the
            decode-side PC; the target buffer's predicted target latches into
            the decode-side target; the I$ and BTB hit flags latch as their
            decode-side counterparts; and the fetch speculation enable
            latches into the decode-side speculation enable.

            Instruction, PC, and predicted target copy through as-is even
            when either hit flag is clear — a per-lane miss is recorded only
            as a flag on the captured bundle; it does not by itself
            substitute a NOP for that lane.

        2. Stalls and Flush control:

            Update priority on a clock edge (highest wins): reset or flush
            takes first priority and forces both lanes to a NOP bubble
            (NOP instruction, zeroed PCs/targets, all controls cleared).
            Failing that, enable without stall takes second priority and
            captures both lanes per §1, with miss flags passing through
            rather than being forced to NOP. Otherwise the register holds
            its previous decode-side state.

            Reset and flush share one branch and clear identically. Flush
            empties the stage on mispredict or redirect so decode does not
            consume stale instructions after fetch realigns. Stall freezes
            without clearing: fetch may continue presenting, but decode
            keeps the prior pair until back-pressure releases. If enable is
            low, no advance occurs even when stall is low.

S2_Decode:

    Overview:
        Path: `rtl/s2_decode/decode_core_struct.sv`

        Instantiates one dual-ported branch state buffer plus a generate
        block that pairs one decoder with one target predictor per slot
        (two iterations for dual issue). IF/ID supplies instruction, PC,
        predicted target, plus per-lane I$ hit, BTB hit, and speculation
        enable; memory supplies branch-state train ports into the state
        buffer. Decode does not access the register file — only destination
        and source addresses, use/write flags, immediates, predict targets,
        and nest-speculation stall are produced (GPR read/write belongs to
        the issue stage). Besides the decoded fields, the decode struct
        exports a memory-write qualifier and the BHT snapshot (predictor
        state and entry-valid) that rides along to rename as ROB metadata.
        Nested-speculation freeze is produced here and returned to the
        fetch program counter. The decoder's internal jump enable is not
        exported — it only feeds the same-lane target predictor.

    Decoder:
            Path: `rtl/s2_decode/core_mod/decoder.sv`

            // input data
            input  instr_t      instr,
            input  logic        fetch_valid, // I$ hit from IF/ID; 0 => bubble (valid=0)

            // output data
            output opcode_t     opcode,
            output funct3_t     funct3,
            output funct7_t     funct7,
            output gpr_addr_t   rd_addr,
            output gpr_addr_t   rs1_addr,
            output gpr_addr_t   rs2_addr,
            output word_t       imm,

            // output controls
            output logic        valid,     // legal RV-DIS decode and fetch_valid
            output logic        rs1_use,
            output logic        rs2_use,
            output logic        lane_sel,
            output logic        brch_en,
            output logic        jump_en,
            output logic        store_en,
            output logic        reg_write

        0. Structure and Specification:

            The decoder is a purely combinational RV32I scalar decode block
            for one instruction slot — a single instruction word in, no dual
            arrays on this module's own ports. It drives decoded opcode and
            function fields, architectural register indices, a sign-extended
            immediate, and control qualifiers for downstream register read,
            branch prediction, store detection, and dispatch. Field
            extraction and legality tables live in the decode package; the
            module itself is only wiring: raw opcode and funct3 are sampled
            first, then GPR-specific decoders zero unused register fields per
            opcode rules. The I$ hit flag comes from IF/ID; when low, decode
            valid is forced low regardless of the instruction bits so a fetch
            bubble decodes as a squashed slot. Control qualifiers driven per
            slot: valid is the AND of I$ hit and legality, true when the
            instruction is in the implemented RV-DIS scalar subset; branch
            enable covers BRANCH, JAL, and JALR; jump enable covers
            unconditional jumps only (JAL, JALR); store enable covers the
            implemented SW store; source-use flags mark whether an operand
            needs a GPR read; and register-write is asserted when the
            destination is not x0 and the instruction writes a register.

            Jump enable is distinct from branch enable so the target
            predictor can treat direct jumps separately from conditional
            branches. Store enable is broken out from the general opcode
            class so later stages (dispatch, memory) can gate a write-port
            without re-decoding funct3. The decoder does not read the
            register file, predict targets, or issue to execution; that
            integration is in the decode struct and dispatch.

        1. Two Decoders for Instruction Parallelism:

            Dual issue replicates the decoder (and target predictor) once per
            iteration of the slot generate loop inside the decode struct.
            Both run in parallel with no cross-coupling; only the shared
            state buffer ties the two lanes together (dual-ported, one array
            index per lane). Per-lane wiring: I0 pairs the first decoder with
            the first target predictor, fed from IF/ID index 0; I1 pairs the
            second decoder with the second target predictor, fed
            symmetrically from IF/ID index 1.

            Each decoder exports lane select, opcode bundle, immediate,
            valid, branch enable, store enable, source-use flags, and
            register-write into the matching array index of the decode
            struct's outputs; jump enable stays internal and only feeds the
            same-index target predictor. GPR read addresses are exported for
            later stages (issue register file); the decode struct does not
            instantiate a register file. The state buffer also lives here.
            Pairing legality and which lane may fire are decided later in
            dispatch, not inside the decoder.

        2. Instruction Lane Differentiation:

            Lane select tags which execution lane owns the opcode class:
            zero routes to the even lane for OP and OP-IMM scalar ALU
            instructions, while one routes to the odd lane for LOAD, STORE,
            BRANCH, JAL, JALR, LUI, and AUIPC.

            Unknown opcodes default to the even lane but with valid clear
            (the legality table defaults to illegal for any unlisted opcode)
            so dispatch can squash illegal slots. Supported branch compare
            subset: BEQ, BNE, BLT, BGE; memory: LW, SW. Source-use flags
            mark which operands need a later register-file read (issue
            stage); register-write suppresses writes to x0 by checking the
            destination address directly (LOAD additionally requires the LW
            funct3, matching the legal subset).

    Branch State Buffer (State_Buffer):
            Path: `rtl/s2_decode/core_mod/state_buffer.sv`

            // parameters
            parameter integer INDEX_W      = PC_INDEX_AW,
            parameter integer DATA_W       = 2,
            parameter integer WAYS         = 16,
            parameter [1:0]   DEFAULT_STATE = 2'b10,

            // external controls
            input  logic        clk,
            input  logic        rst_n,

            // input data (dual-issue slot pair)
            input  word_t       pc            [2],
            input  logic        brch_en       [2],

            // writeback controls
            input  logic        valid_wb      [2],

            // writeback data
            input  word_t       brch_pc_wb    [2],
            input  br_state_t   brch_state_wb [2],

            // output data
            output br_state_t   brch_state  [2],
            // output controls — bank entry valid (1=trained/hit, 0=miss → DEFAULT_STATE)
            output logic        state_valid [2]

        0. Structure and Specification:

            The state buffer is the branch-direction predictor table (BHT).
            Instantiated once inside the decode struct as a single dual-
            ported module, not two per-lane instances. It stores a 2-bit
            saturating counter state per branch PC, indexed like the BTB:
            13-bit index over PC[14:2], 8192 slots, 512 sets × 16 ways (see
            shared geometry in S1_Fetch). Each bank entry is 33 bits: valid
            plus 2-bit state. Set/way decode uses the shared cache helpers.
            Miss (valid clear) defaults to weakly taken (2'b10). Lookup PCs
            come from the IF/ID fetch PCs; branch enables are fed back
            combinationally from this same cycle's decoder outputs and gate
            whether a lane performs a real lookup — non-branch instructions
            drive the default state without treating the bank as taken. The
            entry-valid outputs expose the raw bank-entry valid bit per lane
            (independent of branch enable) and are carried forward through
            ID/RN as ROB metadata. Training arrives from execute via the
            writeback train ports with branch PC and updated state.

        1. Branch Predict 2-bit State Encode:

            Each stored entry is a 2-bit saturating counter. Prediction at
            decode uses the high bit of the state: 0 means not taken, 1 means
            taken. Training updates are computed at memory by the state
            lookup table from the current state and resolved outcome (taken
            or not taken), then written into the state buffer on the next
            valid train.

            State encoding:

                00 — strongly not taken (direction: not taken)
                01 — weakly not taken   (direction: not taken)
                10 — weakly taken       (direction: taken; reset default)
                11 — strongly taken     (direction: taken)

            The high bit is what the target predictor reads for direction;
            the low bit marks how strong that guess is.

            On cold miss or reset the bank has no entry, so the read path
            returns weakly taken. Unseen branches are therefore predicted
            taken on first use, but not with full confidence. After execute
            resolves the branch, the next 2-bit value from the current state
            and whether the branch was taken is written back into the state
            buffer on the next valid train.

        2. Combinational Dual Read with Forwarding:

            Both ports look up independently from each lane's fetch PC,
            active whenever that lane's branch enable is set. The forwarded
            entry reads the bank cell unless a valid train in the same cycle
            targets that slot; then the incoming train entry wins (I0 train
            checked before I1). The way read returns the stored 2-bit state
            when the entry's valid bit is set; on miss it returns the default
            weakly-taken state. Entry-valid is that forwarded entry's raw
            valid bit, reported regardless of branch enable. The state output
            applies the branch-enable mux on top: branch lanes expose the
            looked-up state; non-branch lanes force the default. Lookups are
            combinational; predictors see the result in the same cycle as the
            presented fetch PCs.

        3. Sequential Falling-edge Dual Writeback:

            Training commits on the falling clock edge when either train-
            valid is set. The write index is derived from the train branch
            PCs; stored data is the 2-bit train state packed with valid
            forced set. Dual train in one cycle can update two distinct
            slots; if both trains map to the same set/way, both nonblocking
            writes fire and the index-1 update is the final value. Because
            forwarding is evaluated before the edge, a train visible on cycle
            N is readable on port outputs in cycle N even though the bank
            register updates after the edge. On reset the entire bank is
            cleared to zero.

    Branch Target Predictor (Target_Predict):
            Path: `rtl/s2_decode/core_mod/target_predict.sv`

            input  logic        brnch_en,
            input  logic        jump_en,
            input  logic        spec_n,

            // input data
            input  word_t       pc,

            input  word_t       imm,
            input  word_t       pc_target,

            output word_t       pc_predict,

            output logic        pred_valid_wb,

        0. Structure and Specification:

            The target predictor is a purely combinational per-lane block,
            one instruction slot per instance — its own ports carry no dual
            arrays. It is instantiated twice inside the decode struct's slot
            generate loop, each paired with the same-index decoder. The
            state buffer lives in the same struct and feeds that lane's
            direction state into each instance; the IF/ID bundle supplies
            PC, BTB target, and per-lane speculation. The decoder guarantees
            that jump enable implies branch enable, so nest-speculation stall
            reduces to already-speculative AND branch; the module is active
            whenever the slot is a branch/jump and not already speculative.

            Nested speculation guard: if the slot is already speculative
            while it is a branch or jump, the module disables predict/train
            outputs and asserts nest-speculation stall. Top wires each
            lane's nest stall into the fetch program counter so the PC cannot
            start a second speculation while one is outstanding.

            Per-instance wiring (I0 shown; I1 is symmetric): BTB hit from
            IF/ID; branch and jump enables from the same-lane decoder (jump
            is JAL/JALR only, not exported from the struct); already-
            speculative from IF/ID; instruction address from IF/ID; 2-bit
            direction from the state buffer (defaulted on miss); sign-
            extended immediate from the same-lane decoder; and BTB target
            from fetch. On the output side: predict-taken, a BTB train
            request, nest-speculation stall (freezing the PC), and the next
            speculation address.

            When the slot is not an active (non-nested) branch/jump,
            predict-taken and train request deassert and the predicted
            address passes the PC through unchanged. When already speculative
            on a branch/jump slot, the same quiet outputs apply and nest
            stall freezes the program counter via top.

        1. Two Target Predictors for Instruction Parallelism:

            Dual issue is implemented by replicating the same target
            predictor twice in the decode struct's slot loop with no
            cross-coupling between lanes. Instance 0 binds to the first
            decoder's outputs plus IF/ID and state-buffer index 0; instance 1
            binds to the matching index-1 nets. Both instances evaluate in
            parallel every cycle. Each lane can independently assert
            predict-taken, a train request, and a distinct predicted address
            while the other lane is quiescent (non-branch) or active on a
            different PC. Throughput is two independent target-predict
            results per cycle; the program selector in fetch routes each
            lane's taken predict onto that same lane's next-PC base and sets
            the matching sticky speculation flag — not a swap that always
            puts taken on I0 and fall-through on I1.

        2. Branch Target Calculation and Comparison:

            The decode-computed target is the fetch PC plus immediate,
            aligned down to a 4-byte boundary. A stale-BTB check compares
            that decode target against the BTB's predicted target. A BTB
            miss is simply a clear hit flag.

            When the slot is not an active (non-nested) branch/jump, the
            train request stays clear and the predicted address passes the
            PC through unchanged. When it is active: a BTB miss drives a
            train request with the predicted address equal to the decode
            target; a stale BTB likewise drives a train request with the
            decode target; and a clean hit with no staleness leaves the
            train request low with the predicted address equal to the BTB
            target.

            The train request flags a BTB train on BTB miss or decode/BTB
            target mismatch. Direction-state miss uses the default weakly-
            taken state.

        3. Predication from 2-bit State and Control:

            Direction prediction is separate from address selection (see the
            state buffer encoding table above). When the slot is not a branch
            or is already speculative, predict-taken is clear and the
            predicted address equals the PC. When the slot is an active
            unconditional jump, predict-taken is forced set since JAL/JALR
            are always taken. When the slot is an active conditional branch,
            predict-taken follows the high bit of the direction state.

            Nested speculation is guaranteed branch-enable whenever jump-
            enable is set: when already speculative on a branch/jump slot,
            nest stall asserts and the predict outputs go quiet; otherwise
            nest stall stays clear and predict outputs behave normally under
            the active non-nested condition.

            How the loop closes at the top of the core:

            After a branch resolves in memory, the state lookup table chooses
            the next 2-bit predictor state for that branch PC. On writeback,
            decode installs those updated states into the state buffer so
            later fetches see the trained direction. Separately, when decode
            predicts a taken branch or jump, top forwards that decision to
            fetch as predict-taken so the program selector can redirect
            fetch. If decode sees another branch or jump while fetch is
            already speculative, it raises a nest stall into the program
            counter unit, which freezes the program counter until recovery
            clears the outstanding speculation.

S3_Rename:

    Overview:
        Rename maps architectural destinations onto ROB-owned physical tags
        p32..p63 and tracks in-flight instructions in the reorder buffer.
        The stage is built around the ROB: allocation, completion, and
        commit all flow through ROB indices. The Register Alias Table (RAT)
        / Retirement RAT (RRAT) only holds architectural↔physical maps;
        it does not allocate tags. Destination tags are derived from the ROB
        flat index. Reclaim is ROB head advance (and flush). Architectural
        x0..x31 remain on p0..p31 in the RRAT. The rename core glues the
        RAT and ROB together and forwards their combinational outputs
        straight into the RN/DP register.

            List between them). Allocation is gated on not flushing, not
            rename-stalling, not ROB-full, and at least one valid rename

            valid, while RAT allocate enables only rename lanes that
            actually write a register. Branch marking is valid AND branch
            enable. Both retire lanes are offered to the ROB's internal
            eligibility check every cycle when the stage is enabled and not
            flushing.

            The ROB-derived destination tag is presented for every allocated
            instruction (stores and branches included, gated only by ROB
            allocate success), since reservation-station and PRF writeback
            tracking need a ROB tag regardless of register-write; the RAT
            only cares about register-writing allocates. Validity, path-use,
            and physical source tags pass the RAT/ROB combinational outputs
            straight through to the RN/DP register.

            The ROB's per-lane branch-commit enables and path selects collapse
            into scalar path-enable (OR of both lanes) and a single path
            select (lane 1 wins when both commit a branch, matching the RAT's

            the dispatch core's path filter directly for same-cycle reservation-
            station wrong-path squash.

            The RAT holds two speculative architectural-to-physical maps
            (one per speculation path) and one retirement map. Path-use for
            each lane reports which speculative column that instruction is
            reading, following its speculation enable. Reset maps x0..x31 to
            p0..p31 in all three tables; x0 always reads p0. Destination
            tags come from the ROB, not from a Free List; there is no
            old-destination reclaim port. All updates apply on the negative
            clock edge.

        1. Source Register Lookup:

            Source lookup reads only the speculative column selected by that
            instruction's speculation enable; disabled sources and
            architectural x0 return p0. Lane 1 can bypass lane 0's newly
            allocated destination when both lanes select the same path and
            lane 1 reads lane 0's destination. Cross-path bypass does not
            occur.

        2. Destination Register Rename:

            A legal allocate (enabled and not writing architectural x0)
            writes the ROB-derived tag into the selected speculative map for
            that architectural destination. If both lanes rename the same
            register on the same path, lane 1 (younger) wins because its
            write is applied after lane 0's in the same sequential update.

        3. Commit to the Retirement RAT:

            A legal RRAT commit (enabled and not writing architectural x0)
            writes the exact ROB head PRF tag into the retirement map for
            that architectural register. The live speculative RAT is never
            read for commit, because a younger rename may already own that
            architectural register. Dual commit updates both RRAT entries in
            program order within the same falling edge; same-destination dual
            commit keeps lane 1's write.

        4. Branch Resolution and Recovery:

            Branch-commit enable and path select come from ROB commit of a
            branch. Lane 1 is checked first: its path select copies one
            speculative map into the other (or the reverse); lane 0 only
            applies when lane 1's branch-commit is inactive. Lane 1 is
            younger and so has final priority when both branches resolve in
            the same cycle. Flush restores both speculative maps from the
            retirement map (no Free List rebuild).

        0. Structure and Specification:

            The ROB is a 32-entry circular queue, stored as one bank of
            16 rows by 2 ways with a separate valid-bit array. Flat index
            maps to PRF tag p32..p63. Head and tail pointers carry an extra
            wrap bit so occupancy is tail minus head. Stall asserts when
            occupancy leaves fewer than two free slots, so a dual-issue pair
            always has room.

            Each valid entry holds retirement control only: complete,
            register-write, branch and store type bits, speculation path, the
            decode-time branch-predictor snapshot, architectural destination,
            and branch-taken. Payload and valid bits are separate; flush or
            reset clears pointers and valid (stale payload is ignored).

            The module is internally split into two pure-combinational peers
            that mirror each other structurally: the tail allocator and the
            head retirer (probed from the registered bank). The reorder
            buffer itself owns only the falling-edge-latched storage (bank,
            valid bits, head, tail, active speculation path) and applies both
            peers' decisions in one sequential update.

            Timing model (no rising-edge ROB stage) — chosen so head and
            tail can move together without hazarding a same-cycle rename
            versus retire:

              Combinational — from the registered ROB state only:
                          • retire eligibility and commit buses from the
                            head retirer
                          • rename allocation tags from the tail and allocate
                            success flags from the allocator
                          • next head / tail / active-speculation from those
                            decisions
                        Head reads and tail tags therefore do not wait on a
                        rising-edge ROB pipeline stage.

              Falling edge — single storage update that applies, in order:
                          1. writeback (complete and branch-taken only)
                          2. commit reclaim at head (clears valid)
                          3. packed rename allocate at tail
                          4. pointer / active-speculation latch
                        Writeback is the barrier between "just allocated" and
                        "eligible to retire": an entry allocated this cycle
                        remains incomplete until a later writeback, so reclaim
                        cannot touch the same logical instruction as a
                        same-cycle allocate even though both updates share the
                        falling edge.

            Head (retire) and tail (allocate) are independent: a new entry
            always starts incomplete, so it cannot retire until writeback.
            That allows same-cycle parallel reclaim and allocation at
            opposite ends.

        1. Allocation (rename → tail):

            Combinational destination tags are the packed PRF tags for the
            next free slot(s) at the tail, computed for both lanes regardless
            of allocate enable (the caller gates use via allocate success).
            Allocates pack contiguously: one or two instructions per cycle.
            Only enabled lanes assert write enables. New entries start
            incomplete. Speculation enable is stored as the entry's path bit
            (clear → path0, set → path1). Storage updates on the falling
            edge together with writeback and reclaim — no extra rising-edge
            ROB stage.

        2. Writeback (completion):

            Writeback addresses an entry by its PRF-wide ROB tag, marks it
            complete, and records branch-taken for branches. No execution
            result data is stored in the ROB (results go to the physical
            register file). Complete is written on the falling edge only —
            there is no same-cycle writeback bypass into the retire path.
            Eligibility appears the cycle after writeback (Execute →
            Writeback → Retire).

        3. Retire eligibility and commit:

            Eligibility is combinational from registered ROB state only,
            probed as head and head-plus-one (no same-cycle writeback
            bypass): the older head entry is ready when valid and complete;
            the younger head entry is ready only when the older is ready and
            that younger entry is also valid and complete. There is no
            standalone can-retire output; the module folds eligibility
            directly into the commit strobes (retire offered AND ready AND
            on-path), which drive reclaim / head advance and gate every
            commit bus below. Both retire lanes are offered every cycle by
            rename when enabled and not flushing; the ROB decides how many
            actually commit.

            Commit buses (combinational on the commit strobes):
              RRAT update (enable, architectural destination, PRF tag)
              branch path sync (enable and path select)
              store-buffer strobe

            Wrong-path valid entries do not commit side effects; recovery is
            by flush (or later wrong-path drain policy). In-order dual commit
            never fires lane 1 without lane 0 in practice, since retire is
            offered identically for both lanes and younger readiness already
            requires older readiness.

        4. Branch path tracking:

            One registered active-speculation bit tracks the committed path
            (initially path0). When a correct-path branch commits, its
            branch-taken outcome becomes the next active path and is reported
            on the branch-commit enable / path-select bus. The second head
            entry is evaluated against the path after the first commit, so
            two completed branches can resolve in one cycle; lane 1 wins if
            both resolve.

        5. Reclaim (no Free List):

            On commit, only the head valid bit(s) clear and the head pointer
            advances by the number of commits (1 or 2). The PRF tag tied to
            that ROB slot becomes reusable when the circular queue wraps and
            rename reallocates the same flat index. There is no separate
            free-tag return path.

S4_Dispatch:

    Overview:

        Renamed dual-issue instructions enter dispatch through two peers
        glued by the dispatch core: the reservation station and the physical
        register file. The RS owns the bank and select logic (bank not
        ported). The bank stores controls and physical tags only (no operand
        data). Selection is combinational: up to two oldest ready bank
        entries and two ready rename lanes form a four-candidate pool; the
        two oldest issue. Internal clear / age / rename-store controls update
        the bank on the falling edge. Operand values are read from the
        physical register file at issue and buffered in the DP/EX register,
        which demultiplexes the dual issue pair onto four execution ports
        (even0 / even1 / odd0 / odd1) by lane select.

        Glue: `rtl/s4_dispatch/dispatch_core.sv`
          peers: reservation_station | physical_register
        Helpers: `rtl/s4_dispatch/funct_pkg/rs.sv`

            // dispatch_core external API (dual [2] arrays)
            input  logic        clk, rst_n, enable, flush_rs,
            input  logic        path_en, path_sel,
            input  logic        rob_valid_dp [2], path_use_dp [2], lane_sel_dp [2],
            input  opcode_t     opcode_dp [2],
            input  funct3_t     funct3_dp [2],
            input  funct7_t     funct7_dp [2],
            input  prf_addr_t   ps1_tag_dp [2], ps2_tag_dp [2], rob_tag_dp [2],
            input  word_t       imm_dp [2], pc_dp [2],
            input  logic        wb_en [2],
            input  prf_addr_t   rob_tag_wb [2],
            input  word_t       wb_data [2],
            output logic        stall_dp,
            output logic        valid [2], lane_sel [2], reg_write [2],
            output opcode_t     opcode [2],
            output funct3_t     funct3 [2],
            output funct7_t     funct7 [2],

            output word_t       imm [2], pc [2],
            output word_t       rs1_data [2], rs2_data [2]

        Within a cycle:
          combinational — wakeup view, readiness, 4→2 age pick, issue mux,
                          physical register-file read
          falling edge  — reservation-station bank apply (clear / age /
                          rename store) and physical register-file writeback

        Glue wiring: RS drives stall_dp plus issue controls and physical
        source tags; dispatch_core derives reg_write via rs_produces; PRF
        reads those tags and returns operand data on the issue outputs.

    Physical Register File:
            Path: `rtl/s4_dispatch/core_mod/physical_register.sv`
            Module: physical_register
            Depth: 64 physical registers (p0..p63). ROB-owned tags
            p32..p63 hold speculative results; p0..p31 are the architected
            baseline after reset / RRAT commit.

            // dual-issue ports are [2] arrays (I0 / I1)
            input  logic        clk, rst_n,
            input  prf_addr_t   rs1_addr [2],
            input  prf_addr_t   rs2_addr [2],
            input  logic        wb_en    [2],
            input  prf_addr_t   rob_tag_wb [2],
            input  word_t       wb_data  [2],
            output word_t       rs1_data [2],
            output word_t       rs2_data [2]

        0. Structure and Specification:

            Dual-issue physical register file: four combinational read ports
            and two writeback ports, addressed by physical register tags.
            Storage covers p1 through p63; p0 is not stored and always reads
            as zero (architectural x0). Writes to tag zero are ignored.

        1. Read path and same-cycle writeback bypass:

            Each port reads combinationally from the addressed physical
            register. Unused sources arrive as p0 and read zero. Used sources
            read the stored value (or zero for p0), then apply same-cycle
            bypass from either writeback lane: if both hit the same
            destination, the younger (I1) data wins; else I1 hit wins; else
            I0 hit; else the stored value. Bypass lets the DP/EX register
            capture the same-cycle writeback value when latching issue
            operands before the falling-edge array commit.

        2. Writeback commit (falling edge):

            The physical register array updates on the falling clock edge.
            Same-destination dual writeback commits I1 only (I0 suppressed).
            Independent destinations commit both lanes. Reset clears p1
            through p63 to zero.

    Reservation Station:
            Path: `rtl/s4_dispatch/core_mod/reservation_station.sv`
            Helpers: `rtl/s4_dispatch/funct_pkg/rs.sv`
            Geometry: 16 fully associative ways; dispatch-order ages in the bank
            Owns: bank + select (ready / 4→2 pick / issue mux); bank not ported

            input  logic        clk, rst_n, enable, flush,
            input  logic        path_en, path_sel,

            input  logic        valid_dp [2], lane_sel_dp [2], path_use_dp [2],
            input  opcode_t     opcode_dp [2],
            input  funct3_t     funct3_dp [2],
            input  funct7_t     funct7_dp [2],
            input  prf_addr_t   ps1_tag_dp [2], ps2_tag_dp [2], rob_tag_dp [2],
            input  word_t       imm_dp [2], pc_dp [2],

            input  logic        wb_en [2],
            input  prf_addr_t   rob_tag_wb [2],

            output logic        stall_dp,
            output logic        iss_valid [2], iss_lane_sel [2],
            output opcode_t     iss_opcode [2],
            output funct3_t     iss_funct3 [2],
            output funct7_t     iss_funct7 [2],
            output prf_addr_t   iss_prd [2],
            output word_t       iss_imm [2], iss_pc [2],
            output prf_addr_t   ps1_prf [2], ps2_prf [2]

        0. Structure and Specification:

            The reservation station is a dual-issue centralized queue of 16
            ways plus the former selector logic. Registered bank fields
            (updated only on the falling clock edge) include: valid, stamped
            way tag, age, lane select, speculation path, both source-ready
            bits, opcode and function fields, physical source tags,
            destination tag, immediate, and PC. Operand data is never stored.
            The bank arrays are module-internal (not ports).

            Each entry's stamped way tag is the way id written at allocate;
            internal clear / age / issue tags address the entry by that
            stored tag. Ages live only in the bank age field (no free-running
            age counter). Pure helpers live in rs_pkg (rs_wake_bit,
            rs_path_ok, rs_way_kill, rs_disp_ready, rs_pick_oldest /
            rs_pick_oldest4, rs_free_ways, rs_alloc_src_rdy, …).

        1. Combinational select (ready → pick → issue):

            Wakeup view ORs writeback hits onto registered ready bits
            (rs_wake_bit). Bank issue readiness requires a valid entry with
            both sources ready or satisfied by same-cycle writeback, after
            the path filter masks wrong-path entries. Rename readiness checks
            the bank destination CAM plus writeback, with same-pair
            read-after-write forcing I1 unready when I0 produces a tag I1
            reads. Up to two oldest ready bank ways and two ready rename
            lanes form the four-candidate pool (C_RS0, C_RS1, C_BY0, C_BY1).
            Rename ages are younger than every live bank age so waiting bank
            entries win ties.

            The two oldest candidates issue (bank payload when sourced from
            the bank, rename lane when sourced from rename). Unpicked ready
            rename stores into the bank on the falling edge. Issued rename is
            a nop (no stub; the destination is in flight without occupying a
            way). Issued bank entry clears that way on the falling edge.
            Unpicked bank candidate (in the pool but not issued) age-bumps
            only.

            Clears plus rename stores must fit in two internal control
            channels (src_en / store_en / rs_tag); if an age pick would
            overflow, the select drops the youngest bank pick and may refill
            with a ready rename. Dispatch stalls when not flushing and
            unpicked renames need more free ways than available (crediting
            same-cycle writeback frees via rs_free_ways).

            The issue mux selects bank or rename payload for each fired slot
            and drives iss_* controls plus ps1_prf / ps2_prf for the physical
            register-file read. Register-write is derived in dispatch_core
            via rs_produces.

        2. Falling-edge bank update:

            Dual-channel internal control intents per channel: write a rename
            lane into a free way (src_en=0, store_en=1); bump age only for an
            unpicked bank candidate (1,1); nop (0,0 — rename already issued
            or idle); clear a bank entry that just issued (1,0). Clear / age
            use the stamped way tag.

            When enabled: apply wakeup ready bits, free writeback-matching
            destinations and wrong-path entries (rs_way_kill), then decode
            the two control channels. Rename stores (blocked by stall_dp)
            allocate into the lowest free ways, stamp the way tag, and set
            ready bits from writeback, the bank destination CAM, and
            same-pair read-after-write. Flush or reset clears the bank.

        3. Recovery:

            On reset or reservation-station flush at the falling edge, the
            bank clears. The path filter continuously drops wrong-path rename
            stores and may squash wrong-path bank entries. Finer younger-only
            flush by speculation context remains a future refinement.

Intermediate Register (DP_EX):
            Path: `rtl/s5_execution/dp_ex.sv`

            // dual [2] arrays from RS issue (dual) + PRF read data
            input  logic        clk, rst_n, enable, flush, stall,

            input  logic        valid     [2], lane_sel  [2], reg_write [2],
            input  opcode_t     opcode    [2],
            input  funct3_t     funct3    [2],
            input  funct7_t     funct7    [2],
            input  prf_addr_t   rob_tag   [2],   // ROB-owned dest tag (no
                                                  // separate prd / rob_idx)
            input  word_t       imm       [2], pc [2],
            input  word_t       rs1_data  [2], rs2_data [2],   // from PRF

            output logic        ev_enable_ex    [2], ev_reg_write_ex [2],
            output opcode_t     ev_opcode_ex    [2],
            output funct3_t     ev_funct3_ex    [2],
            output funct7_t     ev_funct7_ex    [2],
            output prf_addr_t   ev_prd_ex       [2],
            output word_t       ev_imm_ex       [2], ev_pc_ex [2],
            output word_t       ev_rs1_data_ex  [2], ev_rs2_data_ex [2],

            output logic        od_enable_ex    [2], od_reg_write_ex [2],
            output opcode_t     od_opcode_ex    [2],
            output funct3_t     od_funct3_ex    [2],   // odd carries no
                                                        // funct7 output
            output prf_addr_t   od_prd_ex       [2],
            output word_t       od_imm_ex       [2], od_pc_ex [2],
            output word_t       od_rs1_data_ex  [2], od_rs2_data_ex [2]

        0. Structure and Specification:

            The DP/EX register demultiplexes the dual issue / physical-
            register-file-read bundle onto four internal ports (even0,
            even1, odd0, odd1, plus a none sentinel) using a combinational
            port pick: for each dual slot, even lane select claims the next
            free even port (even0 then even1), odd lane select claims the
            next free odd port (odd0 then odd1). Slot 0 is tried first, so it
            always wins the first port of its lane; slot 1 spills to the
            second port only if it picks the same lane as slot 0.

            Per-port staging is built combinationally from whichever dual
            slot mapped to that port (defaulting to zero / not-enabled for an
            unclaimed port), then captured into registers on the rising clock
            edge. The four registered ports are continuously unpacked onto
            the even and odd dual arrays that feed execute. Odd ports never
            carry funct7 — there is no odd funct7 path, matching the odd
            lane's RV32I subset (load / store / branch / jump / LUI / AUIPC
            never need funct7).

        1. Backpressure and Recovery:

            Stall holds the four registered ports at their prior value.
            Reset or flush clears all four ports (enables and register-writes
            cleared, others to zero). When enabled and not stalled, both
            dual-issue inputs are accepted and demultiplexed atomically for
            the next cycle. Same-cycle dual even, dual odd, or one-even /
            one-odd pairs are all legal; a same-lane dual pair uses both
            ports of that lane in slot order.

S5_Execution:

    Overview:

        Path: `rtl/s5_execution/execute_core_struct.sv`

        Four purely combinational lanes (even0 / even1 / odd0 / odd1);
        operands already arrive latched from the DP/EX register, so this
        stage only computes ALU / branch condition / memory address and
        holds no state of its own. Odd-lane link detect (JAL / JALR) is
        computed in the execute glue from odd enable and opcode, not inside
        the odd lane. Two even-lane and two odd-lane instances run in
        parallel for dual issue.

    Even Unit (even_lane):
            Path: `rtl/s5_execution/core_mod/even_units/even_lane_struct.sv`
            Sub-helper: `rtl/s5_execution/core_mod/even_units/scalar_alu_unit.sv`

            input  logic        enable,
            input  opcode_t     opcode,
            input  funct3_t     funct3,
            input  funct7_t     funct7,
            input  word_t       rs1_data, rs2_data, imm,
            output word_t       alu_result

        0. Structure and Specification:

            Scalar RV32I OP / OP-IMM ALU only — upstream reservation-station /
            selector routing guarantees only add / sub / shift / compare /
            logic ops reach this lane. Operand A is always the first source
            data; operand B is the second source for register-register OP,
            otherwise the immediate (OP-IMM). The scalar ALU decodes funct3 /
            funct7 into ADD / SUB (funct7 distinguishes them only for
            register-register OP), SLL, SLT (signed), XOR, SRL / SRA
            (funct7-selected, signed shift kept self-determined to avoid an
            accidental logical shift), OR, AND; any other opcode falls
            through to A plus B.

    Odd Unit (odd_lane):
            Path: `rtl/s5_execution/core_mod/odd_units/odd_lane_struct.sv`
            Sub-helpers:
              `rtl/s5_execution/core_mod/odd_units/branch_target_unit.sv`
              `rtl/s5_execution/core_mod/odd_units/memory_address_unit.sv`

            input  logic        enable,
            input  opcode_t     opcode,
            input  funct3_t     funct3,
            input  word_t       rs1_data, rs2_data, imm, pc,
            output logic        brch_taken, mem_en, mem_write,
            output word_t       brch_pc, mem_addr, mem_wdata,
            output mem_besel_t  mem_besel,
            output word_t       link_pc, reg_wdata

        0. Structure and Specification:

            Handles everything not on the even lane: LOAD / STORE effective
            address, BRANCH condition and target, JAL / JALR link and target,
            and LUI / AUIPC result. Operand A is the first source data;
            operand B is the second source for STORE / BRANCH (register
            compare / store data source), else the immediate. The branch
            target unit evaluates BEQ / BNE / BLT / BGE (signed) against both
            operands into a branch condition. The memory address unit
            computes effective address as A plus immediate, derives store
            write data from operand B for STORE (else immediate, unused), and
            sets byte enables from funct3 — only LW / SW are implemented
            (byte / halfword cases are present only as comments, not yet
            wired). Memory enable is set when the slot is enabled and the
            opcode is LOAD or STORE; memory write is set for STORE. Branch
            taken is set when enabled and either a conditional branch
            condition holds or the opcode is JAL / JALR. Branch PC is A plus
            immediate with the low bit cleared for JALR, else PC plus
            immediate (BRANCH / JAL). Link PC is PC plus four. Register write
            data — merged into the odd ALU result by the struct — is PC plus
            immediate for AUIPC, else the immediate (covers LUI and is
            otherwise unused, since LOAD / BRANCH / JAL / JALR do not route
            through that path).

S6_Memory:

    Overview:

        Path: `rtl/s6_memory/`

        This stage holds the odd-lane EX→MEM pipeline register, the L1 data
        cache (wrapped by the memory core struct), and the two branch-outcome
        state lookup tables. The even lane's ALU result is already final at
        execute and bypasses S6 entirely — it is carried straight into the
        writeback stage's EX bank instead. The EX/MEM register and state
        lookup tables are instantiated directly in the top unit, not inside
        the memory core struct.

    Intermediate Register (EX_MEM):
            Path: `rtl/s6_memory/ex_mem.sv`

            Odd-lane copies only (od0/od1). Unlike the DP/EX register, these
            ports are still scalar per-slot signals, not dual arrays — the
            array conversion done at S4/S5 has not reached this module.
            Pattern below is shown once for od0; od1 mirrors it.

        0. Structure and Specification:

            Two independent registered slices, one per odd issue slot, each
            gated by its own per-slot stall — top stalls a slot only when the
            data cache is busy and that slot has a pending memory access,
            letting a non-memory odd op in the other slot advance during a
            miss. Register-write, branch-taken, memory-enable, and memory-
            write are all captured pre-ANDed with the execute enable, so a
            bubble also zeroes every derived control bit downstream. Reset or
            flush clears both slices to zero.

            Path: `rtl/s6_memory/memory_core_struct.sv`

            Wraps only the memory cache; repacks the two per-slot MEM-stage
            requests into the cache's generic dual ports.

            input  logic        clk, rst_n, enable,

            Each port's access type is write when memory-enabled and

            spurious access. One memory cache is instantiated and its busy
            flag is passed through as data-cache busy.

    Memory Cache (memory_cache):
            Path: `rtl/s6_memory/core/memory_cache.sv`

            parameter integer BYTE_COUNT = M_SIZE/8, LINE_BYTES = 32,
                              INDEX_W = PC_INDEX_AW, DATA_W = RLEN,
                              WAYS = 16, L2_FILL_CYCLES = 4,
                      bit     COLD_L1_RESET = 1,

            input  wire        clk, rst_n, enable,
            input  wire        i0_act, i1_act,        // 1 = write, 0 = read
            input  word_t      i0_addr, i0_wdata,
            input  mem_besel_t i0_besel,
            input  word_t      i1_addr, i1_wdata,
            input  mem_besel_t i1_besel,
            output reg  [31:0] i0_mem_data, i1_mem_data,
            output wire        cache_busy

        0. Structure and Specification:

            Port 0 is the older, port 1 the younger dual-issue memory op. A
            fully-associative L1 word bank (geometry from the shared cache
            helpers, indexed by the PC index width and 16 ways) caches
            individual words with a valid bit; a separate per-line warm
            bitmap tracks which cache lines have been bulk-filled. The
            backing store is a flat byte array, standing in for L2 / main
            memory. A port hits when the request is qualified and the entry
            is valid, the line is warm, or that line just finished filling
            this cycle.

            A miss while idle starts a fill sequence lasting four cycles; on
            fill done every word of the missed line is bulk-copied from the
            backing store into the tag bank and the line is marked warm.
            Cache busy is high for the whole fill window plus the idle cycle
            a new miss is first detected, and top wires that busy into
            execute stall so dispatch / execute freeze during a miss.

        1. Ordering hazards handled combinationally:

            Write-after-write — same word, overlapping byte enables on both
            ports suppresses the older (I0) write so the younger (I1) write
            wins. Write-after-read — reads are combinational off the
            pre-write array / bank, so an I0 load sees the pre-store value
            even when I1 stores to the same address in the same cycle; the
            store itself commits at the rising clock edge. Read-after-write
            and in-order memory arrival are assumed enforced upstream by
            dispatch stall / replay — this cache does not reorder or
            hazard-check across cycles on its own.

    Branch State Transition Lookup (state_LUT):
            Path: `rtl/s6_memory/core/state_lookup.sv`

            input  br_state_t state,
            input  logic      pc_sctrl,   // 1 = branch/jump taken (from MEM)
            output br_state_t next_state

        0. Structure and Specification:

            Combinational 2-bit bimodal predictor transition table (current
            state and taken/not-taken outcome select the next state); no
            internal state is stored in this module. Instantiated twice
            directly in the top unit (one per dual-issue slot), driven by
            the memory-stage branch-taken outcome and feeding the updated
            predictor state back to the decode-stage state buffer training
            port.

S7_Wback:

    Overview:

        There is no separate retire module. The single module doing both
        writeback register-stage duty and the physical-register-file-write /
        ROB-complete merge is the EX/MEM/WB stage. It contains its own
        one-cycle EX/WB register for the even lane and MEM/WB register for
        the odd lane, then merges lane 0 / lane 1 into push (PRF write) and
        complete (ROB complete) pairs — but see note 2 below: the merge does
        not actually consume those internal registers.

            output prf_addr_t   push0_rd_addr,
            output word_t       push0_wdata, push0_pc,
            output prf_addr_t   push1_rd_addr,
            output word_t       push1_wdata, push1_pc,
            output prf_addr_t   cmt0_rd_addr, cmt1_rd_addr

        0. Odd-lane writeback mux:

            A completing load is register-write with memory enable and not
            memory write. Odd write data selects load data for a load, else
            PC plus four for a completing JAL / JALR (link), else the ALU /
            AUIPC / LUI result forwarded through the odd lane. This
            combinational mux is what the MEM/WB register captures and is
            also the value merged into the push / complete buses below.

        1. Registers (EX/WB even, MEM/WB odd):

            Two independent sequential blocks: one latches even-lane
            register-write, destination tag, write data, and PC into the
            EX/WB-suffixed outputs; the other latches odd-lane register-
            write, destination tag, the muxed write data above, and PC into
            internal MEM/WB signals. Both clear on reset or flush and hold
            when not enabled.

        2. 4-way merge → push / complete (even-lane priority per slot):

            Each push valid is enable AND (even register-write OR odd
            register-write); destination, data, and PC select the even value
            when even register-write is set, else the odd value. Each
            complete valid is enable AND (even enable OR odd enable) and
            fires for any finishing op — loads, stores, and branches
            included, not just register writes — selecting the destination
            tag the same way.

            Note: this merge reads the same-cycle even execute and odd memory
            inputs (and the odd write-data mux) directly — it does not read
            the EX/WB / MEM/WB registers described in note 1. In the top
            unit, the EX/WB-suffixed even outputs, the odd write-data
            outputs, and the push PC ports are all left unconnected. So the
            registers inside the writeback stage currently have no observable
            effect on the core — push and complete (which drive physical
            register-file write and ROB completion) are purely combinational
            functions of this cycle's execute / memory-stage inputs.
