    | Design choice              | Rationale                                              |
    |----------------------------|--------------------------------------------------------|
    | Fixed 32-bit instructions  | Simpler fetch/decode; no mixed instruction lengths     |

        0. Structure and Specification:

            The PC unit (`rtl/s1_fetch/pc.sv`) is a registered dual-issue address generator.
            It owns two 32-bit byte addresses, pc0_out and pc1_out, that name the
            instruction pair fetched on the even (I0) and odd (I1) lanes. The module is
            intentionally narrow: it does not decode branches or read the BTB. It only
            (1) aligns incoming bases pc0_in / pc1_in to 4-byte boundaries, (2) adds a
            selected increment when enabled and not stalled, and (3) latches the result on
            the clock edge. Branch targets, fall-through PCs, and recovery addresses are
            supplied by pc_selector; fetch_stall and dispatch_stall come from the fetch
            and dispatch stages. On reset, pc0_out <= RESET_PC and pc1_out <= RESET_PC+4,
            establishing the canonical dual-issue layout where I1 trails I0 by one word.
            The is_spec output is a registered flag that records whether the current PC
            pair was advanced under speculative control (spec0_en).

        1. Dual PC adder with mode selection:

            Both lanes share one combinational next-value path. After alignment,
            pc0_a = {pc0_in[31:2], 2'b00} and pc1_a = {pc1_in[31:2], 2'b00}. When
            enable is high and neither stall is asserted, mode selects the increment
            applied to both lanes in parallel:

            | mode | Name                  | pc0_next      | pc1_next      | Use case                                      |
            |------|-----------------------|---------------|---------------|-----------------------------------------------|
            | 0    | sequential dual-issue | pc0_a + 8     | pc1_a + 8     | straight-line fetch; next 8-byte bundle       |
            | 1    | speculative / split   | pc0_a + 4     | pc1_a + 4     | divergent pc0_in / pc1_in from pc_selector    |

            mode=0 advances each aligned base by one full 8-byte pair (two 32-bit
            instructions). mode=1 tracks two independent +4 streams when pc_selector
            has routed different targets into pc0_in and pc1_in. If enable is low or
            either fetch_stall or dispatch_stall is high, pc0_next and pc1_next hold
            the current registered outputs; the PC pair does not move.

        2. Branch Speculation and Stalls Behavior:

            Speculation is a cross-module contract between pc_selector and `pc.sv`, not
            logic inside the PC adder itself. pc_selector drives pc0_in / pc1_in, mode,
            spec0_en, and fetch_stall; `pc.sv` consumes those signals and exposes is_spec
            back to the selector.

            | Signal          | Direction   | Role                                                                 |
            |-----------------|-------------|----------------------------------------------------------------------|
            | spec0_en        | sel -> pc    | Enter/remain in speculative fetch; latched as is_spec on update      |
            | is_spec         | pc -> sel    | While set, new predict asserts fetch_stall (no nested speculation)   |
            | fetch_stall     | sel -> pc    | Freeze PC pair during unresolved speculation                         |
            | dispatch_stall  | dispatch->pc | Freeze PC independently (BTB train, dispatch back-pressure); keeps is_spec |
            | mode            | sel -> pc    | +8/+8 (0) vs +4/+4 (1) increment selection                           |

            On branch recovery (i0_brch_recover or i1_brch_recover), pc_selector reloads
            pc0_in / pc1_in from execute-stage PCs, clears speculation via spec0_en, and
            sets mode=0 so the next enabled cycle resumes +8/+8 sequential advance from
            the recovered pair. Wrong predictions fall back to the execute address;
            correct predictions continue from the recovered stream with flush handled
            downstream in decode/dispatch, not inside `pc.sv`.

        0. Structure and Specification:

            pc_selector (`rtl/s1_fetch/core_mod/pc_selector.sv`) is a purely combinational
            routing block between the registered PC pair, the branch target buffer, and
            execute-stage recovery. It does not increment addresses; that is `pc.sv`'s
            job. Each cycle it observes the live fetch PCs (pc0_in, pc1_in), BTB targets
            (i0_pc_target, i1_pc_target), and resolved execute PCs (i0_pc_execute,
            i1_pc_execute), then drives pc0_out / pc1_out as the aligned bases that `pc.sv`
            will add to on the next enabled update. It also exports three control signals
            consumed by `pc.sv`: stall (wired as fetch_stall in fetch_core_struct),
            mode, and spec0_en. The registered is_spec flag from `pc.sv` is fed back so
            the selector can block nested predicts while a prior speculation is still
            in flight.

        1. Dual PC Selection Priority without speculation:

            With no predict and no recovery active, the default path simply aligns the
            current fetch pair: pc0_out = align(pc0_in), pc1_out = align(pc1_in). All
            targets and execute addresses are ignored. This is the straight-line case
            where `pc.sv` will apply mode=0 and advance both lanes by +8 from these bases.

            When a predict is taken, selection follows fixed priority (recovery overrides
            predict; see sections 3 and 4):

            | Condition           | pc0_out                  | pc1_out                         |
            |---------------------|--------------------------|---------------------------------|
            | i0_pred && i1_pred  | align(i0_pc_target)      | align(i0_pc_target) + 4         |
            | i0_pred only        | align(i0_pc_target)      | align(pc1_in)                   |
            | i1_pred only        | align(i1_pc_target)      | align(pc0_in)                   |

            The both-taken case forms a contiguous target pair from I0's BTB entry. The
            single-lane cases keep the other slot on its sequential in-pair PC so one lane
            follows the predicted target while the other retains fall-through.

        2. Mode and Control signals:

            Three outputs encode how `pc.sv` should treat the next update:

            | Output   | Asserted when                                      | Effect on `pc.sv`                          |
            |----------|----------------------------------------------------|------------------------------------------|
            | spec0_en | predict taken (unless recovery)                  | latched as is_spec on enabled update     |
            | mode     | exactly one of i0_pred / i1_pred (XOR)           | +4/+4 advance; 0 -> +8/+8 or recovery   |
            | stall    | new predict while is_spec already set              | fetch_stall; freezes PC pair             |

            All three are suppressed when recover_any = i0_brch_recover | i1_brch_recover
            is true, so recovery always returns control to non-speculative +8/+8 stepping.

        3. Branch Speculation and Stalls Behavior:

            Predict vs mode interaction in `pc.sv`:

            | i0_pred | i1_pred | mode (XOR) | `pc.sv` increment | Notes                          |
            |---------|---------|------------|-----------------|--------------------------------|
            | 0       | 0       | 0          | +8 / +8         | straight-line or recovery      |
            | 1       | 0       | 1          | +4 / +4         | split streams                  |
            | 0       | 1       | 1          | +4 / +4         | split streams                  |
            | 1       | 1       | 0          | +8 / +8         | both taken; rerouted target pair |

            A predict-taken asserts spec0_en (unless recovery). While is_spec is set in
            `pc.sv`, any new predict without recovery asserts stall=1, blocking nested
            speculation until execute resolves the outstanding branch. dispatch_stall is
            separate and not generated here.

        4. Branch Recovery and Un-Stalls Behavior:

            Recovery has highest priority in the PC mux:

            | Priority | Condition          | pc0_out                    | pc1_out                         |
            |----------|--------------------|----------------------------|---------------------------------|
            | 1        | i0_brch_recover    | align(i0_pc_execute)       | align(i0_pc_execute) + 4        |
            | 2        | i1_brch_recover    | align(i1_pc_execute)       | align(i1_pc_execute) + 4        |

            Recovery clears spec0_en, mode, and stall in the same cycle, so `pc.sv` resumes
            non-speculative +8/+8 from the recovered bases on the next enabled update.
            Un-stall occurs because recovery deasserts stall and spec0_en while is_spec
            clears in `pc.sv` after the recovered update. Wrong predictions redirect to the
            execute-stage pair; correct predictions realign the fetch window, with pipeline
            flush handled outside pc_selector.

        0. Structure and Specification:

            instruction_cache (`rtl/s1_fetch/core_mod/instruction_cache.sv`) is the
            fetch-stage dual-port instruction store for the 32 KiB RV32I I$ space
            (rv_dis_pkg::I_SIZE). The program counter is byte-addressed
            (ADDR_UNIT_BITS=8), while each bank cell holds one aligned ILEN=32
            little-endian instruction word plus a valid bit (a 33-bit packed entry
            through cache_pkg). INDEX_W = PC_INDEX_AW = 13 selects among 8192 logical
            slots using PC[14:2]. Lookups are combinational; clk and rst_n clear the
            bank on reset. Until sequential miss/refill exists, simulation
            (instruction_cache_tb) or an external loader preloads valid entries. The
            module exposes pc0/pc1 in and instr0/instr1 out and does not yet arbitrate
            misses, refill, or coherence.

        1. 2-way Set-Associative Bank (4-byte instruction word per entry):

            The bank is organized as WAYS=2 (WAY_AW=1, SET_AW=12, SETS=4096): 4096
            sets of two ways, for 8192 x 4 B = 32 KiB of instruction payload.
            cache_pkg::pc_set / pc_way map each fetch PC to one cell with way =
            PC[2] and set = PC[14:3], so each entry stores {valid, instr[31:0]} -
            one full RV32I word, not a single byte. Two-way associativity is chosen
            as the minimum that matches dual-issue fetch: a straight-line pair
            (pc, pc+4) are consecutive word addresses that differ only in PC[2], so
            they land in the same set on ways 0 and 1 and can be read in parallel
            without a same-way bank conflict. An 8-byte aligned dual-issue bundle
            therefore maps onto both ways of one set, which is exactly the
            (pc0, pc1) window produced by `pc.sv`. Each port still indexes
            independently, so any pc0/pc1 pair is legal; the two-way layout makes
            the common sequential dual-fetch case a natural dual hit inside one set.

        2. Combinational Dual Instruction Address Read:

            Both ports read independently in the same cycle. Port I0 indexes
            bank[i0_lookup_set][i0_lookup_way] from pc0; port I1 indexes
            bank[i1_lookup_set][i1_lookup_way] from pc1. Each lookup is
            combinational through cache_way_read: if the selected entry's valid bit
            is set, instrN is the stored word; if valid=0 (cold miss), the default
            data 32'h0 is returned. There is no fall-through PC-based default, so an
            empty slot is indistinguishable from a real all-zero instruction unless
            valid is set.

            Because indexing is direct-mapped by PC set/way (not tag compare), each
            PC maps to exactly one bank location. Dual fetch therefore works for any
            pc0/pc1 pair, including sequential pairs (pc, pc+4) and identical PCs on
            both ports. The two reads do not block each other; they are two parallel
            cache_way_read calls on separate bank cells. In fetch_core_struct, pc0 and
            pc1 from `pc.sv` drive instr0/instr1 into the decode stage on the same cycle
            as the address presentation.

        3. Sequential Cache Instruction Miss (Working Progress):

            Not implemented in current RTL. Planned: sequential miss detect, external
            memory refill, valid install, and fetch stall until both requested lines
            are present.

        0. Structure and Specification:

            target_buffer (`rtl/s1_fetch/core_mod/target_buffer.sv`) is the fetch-stage
            branch target buffer (BTB). Lookups are combinational dual read with
            same-cycle writeback forwarding; the bank trains on negedge clk. The
            module does not decide predict-taken: it only reports per-port hit flags
            (i0_valid / i1_valid) and predicted targets (i0_pc_target / i1_pc_target)
            for downstream fetch/select logic. Execute-stage i0_valid_wb /
            i1_valid_wb qualify training writes that install or overwrite the target
            for the branch PC at WB. clk and rst_n clear the bank on reset.

        1. 16-way Set-Associative Bank (4-byte aligned target per entry):

            The bank is organized as WAYS=16 (WAY_AW=4, SET_AW=9, SETS=512): 512
            sets of sixteen ways, for 8192 logical slots over the same INDEX_W=13 /
            PC[14:2] space as the 32 KiB I$. Each cell is a 33-bit packed entry
            through cache_pkg: {valid, target[31:0]}, where the payload is one
            imm_align4 branch target (not an instruction word). cache_pkg::pc_set /
            pc_way map each lookup or train PC to one cell. Higher associativity than
            the I$ (16-way vs 2-way) gives more distinct branch PCs room in the same
            address window without changing the PC index width. Each port still
            indexes independently, so any i0_pc / i1_pc pair is legal.

        2. Combinational Dual Read with Forwarding:

            Each cycle both ports look up independently from i0_pc and i1_pc. For each
            port, way_with_forward selects bank[set][way] unless a valid WB in the same
            cycle targets that same set/way; then the incoming WB entry wins (I0 WB
            checked before I1 WB). i0_valid / i1_valid are the forwarded entry valid
            bits (entry[DATA_W]) and are independent: a miss or stored valid=0 on one
            port clears only that port's i*_valid. cache_way_read returns the stored
            target when valid=1; on miss (valid=0) it returns 32'h0 for that lane while
            i*_valid stays 0. Lookups are combinational; outputs update in the same
            cycle as the presented fetch PCs.

        3. Sequential Falling-edge Dual Writeback:

            Training commits on the falling clock edge when i0_valid_wb or i1_valid_wb is
            set. The write index is derived from i0_pc_wb / i1_pc_wb; the stored data is
            imm_align4(i0_pc_target_wb / i1_pc_target_wb) with valid forced to 1 via
            cache_set_write. Dual WB in one cycle can update two distinct slots; if both
            trains map to the same set/way, both nonblocking writes fire and the I1
            update is the final value in that slot. Because forwarding is evaluated
            before the edge, a train visible on cycle N is readable on port outputs
            (i*_valid and i*_pc_target) in cycle N even though the bank register updates
            after the edge; the read path always sees the freshest hit/target for
            pc_selector in fetch_core_struct.

        0. Structure and Specification:

            if_id (`rtl/s2_decode/if_id.sv`) is the pipeline register between fetch (IF) and
            decode (ID). An instruction is in IF or ID, not both; this module is the cycle
            boundary where the dual-issue pair is captured for decode. It is a single
            registered stage with no combinational decode; it only stores and forwards
            six fields per lane bundle: instruction word, fetch PC, and fetch-stage
            predicted branch target. pc_target_* is carried alongside the insn so ID and
            later stages can compare against resolved execute targets for mispredict
            recovery. clk/rst_n/enable are the global pipeline controls; flush and stall
            are stage-local back-pressure and redirect inputs from upstream fetch or
            downstream decode/dispatch.

        1. Dual Issue Input and Output:

            Both lanes update together on the same conditions. Six fields per bundle:

            | IF/ID field (input)  | Source (IF stage)     | ID output (latched)   |
            |----------------------|-----------------------|-----------------------|
            | i0_instr_if          | instruction_cache I0  | i0_instr_id           |
            | i1_instr_if          | instruction_cache I1  | i1_instr_id           |
            | i0_pc_if             | `pc.sv` pc0_out         | i0_pc_id              |
            | i1_pc_if             | `pc.sv` pc1_out         | i1_pc_id              |
            | i0_pc_target_if      | target_buffer I0      | i0_pc_target_id       |
            | i1_pc_target_if      | target_buffer I1      | i1_pc_target_id       |

            There is no per-lane enable: I0 and I1 always advance as a pair when the
            stage updates. After predict or recovery reroute, the pair may name divergent
            streams; the register still captures whatever IF drove that cycle.

        2. Stalls and Flush control:

            Update priority in the always_ff block (highest wins on a clock edge):

            | Priority | Condition        | ID register behavior              |
            |----------|------------------|-----------------------------------|
            | 1        | !rst_n           | all outputs cleared to zero       |
            | 2        | flush            | bubble both lanes (clear to zero) |
            | 3        | enable && !stall | capture current IF inputs         |
            | 4        | otherwise        | hold previous ID state            |

            flush empties the stage on mispredict or redirect so decode does not consume
            stale instructions after fetch realigns. stall freezes without clearing. IF
            may continue presenting, but ID keeps the prior pair until back-pressure
            releases. If enable is low, no advance occurs even when stall is low.

        0. Structure and Specification:

            decoder (`rtl/s2_decode/core_mod/decoder.sv`) is a purely combinational
            RV32I scalar decode block for one instruction slot. It accepts a single
            32-bit instr word and drives decoded opcode/funct3/funct7, GPR indices
            (rd, rs1, rs2), a sign-extended immediate, and control qualifiers for
            downstream register read, branch prediction, and dispatch. Field extraction
            and legality tables live in decode_pkg (`rtl/s2_decode/funct_pkg/decode.sv`);
            the module itself is only wiring: raw opcode/funct3 are sampled first, then
            GPR-specific decoders zero unused register fields per opcode rules. Control
            qualifiers driven per slot:

            | Signal    | Definition                                              |
            |-----------|---------------------------------------------------------|
            | valid     | insn is in the implemented RV-DIS scalar subset           |
            | brch_en   | valid && opcode in {BRANCH, JAL, JALR}                   |
            | jump_en   | valid && opcode in {JAL, JALR} (unconditional jumps only)|
            | rs1_use   | operand needs GPR rs1 read                              |
            | rs2_use   | operand needs GPR rs2 read                              |
            | reg_write | insn writes rd (x0 suppressed downstream)               |

            jump_en is distinct from brch_en so target_predict can treat direct jumps
            separately from conditional branches. The decoder does not read the register
            file, predict targets, or issue to execution; that integration is in
            decode_core_struct and dispatch.

        1. Two Decoders for Instruction Parallelism:

            Dual issue replicates decoder twice in s2_decode_struct (u_dec_i0 /
            u_dec_i1). Both run in parallel with no cross-coupling. Per-lane wiring
            inside decode_core_struct:

            | Lane | Decoder   | target_predict      | IF/ID inputs              | state_buffer |
            |------|-----------|---------------------|---------------------------|--------------|
            | I0   | u_dec_i0  | u_target_predict_i0 | i0_pc, i0_pc_target       | i0_target_state |
            | I1   | u_dec_i1  | u_target_predict_i1 | i1_pc, i1_pc_target       | i1_target_state |

            Each decoder exports lane_sel, opcode bundle, imm, valid, brch_en, jump_en,
            rs1_use/rs2_use, and reg_write. GPR read addresses feed register_file and
            are re-exported as i0_rs1_addr / i0_rs2_addr and i1_rs1_addr / i1_rs2_addr
            for dispatch. state_buffer also lives in decode_core_struct. Pairing legality
            and which lane may fire are decided later in dispatch, not inside `decoder.sv`.

        2. Instruction Lane Differentiation:

            lane_sel tags which execution lane owns the opcode class:

            | lane_sel | Execution lane | Opcode classes                          |
            |----------|----------------|-----------------------------------------|
            | 0        | I0 (even)      | OP, OP-IMM (scalar ALU)                 |
            | 1        | I1 (odd)       | LOAD, STORE, BRANCH, JAL, JALR, LUI, AUIPC |

            Unknown opcodes default lane_sel=0 but valid=0 so dispatch can squash
            illegal slots. Supported branch compare subset: BEQ, BNE, BLT, BGE; memory:
            LW, SW. rs1_use and rs2_use gate register-file read enables; reg_write
            suppresses writes to x0.

        0. Structure and Specification:

            register_file (`rtl/s2_decode/core_mod/register_file.sv`) is the dual-issue
            scalar GPR file for RV32I: four combinational read ports (I0 rs1/rs2, I1
            rs1/rs2) and two writeback ports (I0/I1). Physical storage is x1-x31;
            x0 is not stored; reads of x0 always return zero and writes to x0 are
            suppressed. Decode supplies rs1_use/rs2_use and addresses; writeback
            supplies i0_valid_wb/i1_valid_wb, rd, data, and insn PC (i0_pc_wb /
            i1_pc_wb) for same-cycle WAW merge. There is no enable; commits occur
            on the falling clock edge whenever a valid WB targets a nonzero rd. clk/rst_n
            clear the array on reset.

        1. Combinational Dual Read with Forwarding:

            Each read port is independent. Forwarding and WAW merge rules:

            | rs_use | Same-cycle WB to same rd?     | Read data source                          |
            |--------|-------------------------------|-------------------------------------------|
            | 0      | n/a                           | 0 (unused operand)                        |
            | 1      | no                            | regs[addr]                                |
            | 1      | yes (one WB)                  | WB data (bypass)                          |
            | 1      | yes (both lanes, same rd)     | younger insn by i0_pc_wb vs i1_pc_wb      |

            Cross-lane bypass is supported: an ID read on either lane can see the other
            lane's pending WB when addresses match. Bypass is visible before the bank
            updates on the falling write edge.

        2. Sequential Falling-edge Dual Writeback:

            Training commits on negedge clk when i0_valid_wb or i1_valid_wb is set and
            rd != x0. Dual WB can update two distinct registers in one cycle. If both
            lanes write the same rd, only the younger insn (by i0_pc_wb vs i1_pc_wb)
            updates regs[]; the older commit is suppressed. Forwarding on the read path
            still exposes the winning WB value in that cycle before the falling edge.
            After the edge, subsequent reads see the committed value from regs[].

        0. Structure and Specification:

            state_buffer (`rtl/s2_decode/core_mod/brch_predict_units/state_buffer.sv`)
            is the branch-direction predictor table (BHT). Instantiated inside
            decode_core_struct as u_state_buf. It stores a 2-bit saturating counter
            state (br_state_t) per branch PC, indexed like the BTB: INDEX_W = 13 over
            PC[14:2], 8192 slots, 512 sets x 16 ways (see shared geometry table in
            S1_Fetch). Each bank entry is 33 bits: valid plus 2-bit state. Set/way
            decode uses cache_pkg::pc_set and cache_pkg::pc_way. Miss (valid=0) defaults to
            DEFAULT_STATE (2'b10, weakly taken). i0_brch_en / i1_brch_en gate
            whether a lane performs a real lookup; non-branch insns drive
            DEFAULT_STATE on the outputs without treating the bank as taken. WB trains
            from execute via i0_valid_wb / i1_valid_wb with branch PC and updated
            i0_target_state_wb / i1_target_state_wb.


        1. Branch Predict 2-bit State Encode:

            Each stored entry is a 2-bit saturating counter (br_state_t). Prediction at
            decode uses target_state[1]: 0 -> not taken, 1 -> taken. Training updates are
            computed at MEM by state_LUT (`rtl/s5_memory/core/state_lookup.sv`) from the
            current state and resolved outcome pc_sctrl (1 = taken, 0 = not taken), then
            written into state_buffer on the next i0_valid_wb / i1_valid_wb.

            State encoding:

            | State | Name                     | target_state[1] | Predicted direction |
            |-------|--------------------------|-----------------|---------------------|
            | 2'b00 | strongly not taken       | 0               | not taken           |
            | 2'b01 | weakly not taken         | 0               | not taken           |
            | 2'b10 | weakly taken (default)   | 1               | taken               |
            | 2'b11 | strongly taken           | 1               | taken               |

            bit[1] is what target_predict reads: 0 predicts not taken, 1 predicts
            taken. bit[0] marks how strong that guess is. On the not-taken side, 2'b00
            is strongly not taken and 2'b01 is weakly not taken. On the taken side,
            2'b10 is weakly taken and 2'b11 is strongly taken, with the same direction bit,
            different confidence.

            On cold miss or reset the bank has no entry, so the read path returns
            DEFAULT_STATE 2'b10 (weakly taken). Unseen branches are therefore predicted
            taken on first use, but not with full confidence. After execute resolves the
            branch, the next 2-bit value from the current state and whether the branch 
            was taken, that value is written back into state_buffer on the next valid WB. 

        2. Combinational Dual Read with Forwarding:

            Both ports look up independently from i0_pc and i1_pc when brch_en is
            set for that lane. way_with_bypass reads bank[set][way] unless a valid
            WB in the same cycle targets that slot; then the incoming WB entry wins
            (I0 WB checked before I1 WB). cache_way_read returns the stored 2-bit
            state when valid=1; on miss it returns DEFAULT_STATE. The final output
            mux applies brch_en: branch lanes expose raw_state; non-branch lanes
            force DEFAULT_STATE. Lookups are combinational; predictors see the
            result in the same cycle as the presented fetch PCs.

        3. Sequential Rising-edge Dual Writeback:

            Training commits on the rising clock edge when i0_valid_wb or
            i1_valid_wb is set. The write index is i0_pc_wb / i1_pc_wb; stored
            data is the 2-bit i0_target_state_wb / i1_target_state_wb with valid
            forced to 1. Dual WB in one cycle can update two distinct slots; if both
            trains map to the same set/way, both nonblocking writes fire and the I1
            update is the final value. Because forwarding is evaluated before the
            edge, a train visible on cycle N is readable on port outputs in cycle N
            even though the bank register updates after the edge.

        0. Structure and Specification:

            target_predict (`rtl/s2_decode/core_mod/brch_predict_units/target_predict.sv`)
            is a purely combinational per-lane block instantiated twice inside
            decode_core_struct (u_target_predict_i0 / u_target_predict_i1) beside the
            matching decoder. state_buffer lives in the same struct and feeds
            target_state into each instance; the IF/ID bundle supplies pc and
            pc_target per lane. Active when branch_active = pc_valid && (brnch_en | jump_en).

            Per-instance signal map (I0 shown; I1 is symmetric):

            | target_predict port | Wired from                         | Notes                    |
            |---------------------|------------------------------------|--------------------------|
            | pc_valid            | decoder valid                      | legal insn slot          |
            | brnch_en            | decoder brch_en                    | branch or jump           |
            | jump_en             | decoder jump_en                    | JAL / JALR only          |
            | imm                 | decoder imm                        | sign-extended            |
            | pc                  | IF/ID i0_pc                        | insn address             |
            | pc_target           | IF/ID i0_pc_target                 | BTB target from fetch    |
            | target_state        | state_buffer i0_target_state       | 2-bit direction          |
            | set_target          | -> i0_set_target (struct export)   | predict taken            |
            | wb_valid            | -> i0_tp_wb_valid                  | BTB train request        |
            | pc_predict          | -> i0_pc_predict                   | next speculation address |

            When branch_active is low, set_target and wb_valid deassert and pc_predict
            passes pc through unchanged.

        1. Two Target Predictors for Instruction Parallelism:

            Dual issue is implemented by replicating the same target_predict module
            twice in decode_core_struct with no cross-coupling between lanes. I0 binds
            to u_dec_i0 outputs (valid, brch_en, jump_en, imm) plus i0_pc,
            i0_pc_target, and i0_target_state from state_buffer; I1 binds to the
            matching I1 nets. Both instances evaluate in parallel every cycle. Each
            lane can independently assert set_target, wb_valid, and a distinct
            pc_predict while the other lane is quiescent (non-branch) or active on a
            different PC. Throughput is two independent target-predict results per
            cycle; pc_selector in fetch still arbitrates which lane's taken signal
            (i0_pred_taken / i1_pred_taken, driven from set_target in top) wins when
            both predict control flow in the same bundle.

        2. Branch Target Calculation and Comparison:

            decode_target = align4(pc + imm) = { (pc + imm)[31:2], 2'b00 }.
            use_decode_target = (decode_target != pc_target).

            | branch_active | use_decode_target | wb_valid | pc_predict     |
            |---------------|-------------------|----------|----------------|
            | 0             | n/a               | 0        | pc             |
            | 1             | 1                 | 1        | decode_target  |
            | 1             | 0                 | 0        | pc_target      |

            wb_valid flags a BTB train when decode and the latched BTB entry disagree
            (miss, cold entry, or stale target). i0_tp_wb_valid / i1_tp_wb_valid are
            exported for the target_buffer train path; top captures them but fetch-side
            gating from decode mismatch is still TBD.

        3. Predication from 2-bit State and Control:

            Direction prediction is separate from address selection (see state_buffer
            encoding table above).

            | Condition                         | set_target                         |
            |-----------------------------------|------------------------------------|
            | !branch_active                    | 0                                  |
            | branch_active && jump_en          | 1 (JAL/JALR always taken)          |
            | branch_active && !jump_en         | target_state[1] (conditional)    |

            Branch-direction training closes in top: state_LUT at MEM computes
            i0_target_state_wb / i1_target_state_wb; decode_core_struct writes them
            into state_buffer on i0_br_valid_wb / i1_br_valid_wb. In
            `rtl/top/risc_dis_unit.sv`, i0_pred_taken / i1_pred_taken are driven from
            i0_set_target / i1_set_target for fetch speculation via pc_selector.
